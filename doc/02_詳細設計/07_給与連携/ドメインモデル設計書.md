## 1. このコンテキストの責務

**締めた月次勤怠を、給与計算システムが読める 1 行に変換する。**

| 責務 | 対応要件 |
| --- | --- |
| 対象月に在籍していた社員を数え上げ、締め済みの社員だけを出力する | BR-18 / BR-10 |
| 基礎賃金の要る時間と、割増の対象時間を並べる | BR-18 |
| 出力しなかった社員を、理由とともに返す | BR-18 |
| 出力の実行と対象を記録する | BR-18 |
| 割増賃金の基礎額に要る年間の所定を、年ごとに 1 行で出す | BR-18（労基則 19 条 1 項 4 号）|

**担わないもの**

| 担わない | 誰が担うか |
| --- | --- |
| 金額・割増率・単価の計算 | 給与計算システム（2.3 の対象外）|
| 労働時間の集計そのもの | `attendance`。ここは**保存済みの値を読むだけ** |
| 締め状態と月次勤怠の状態 | `approval` |
| 所定労働日数・出勤日数・欠勤日数の数え方 | `attendance`（3.3）|

### 1.1 なぜ新しいコンテキストにするか

出力する 1 行は **4 つのコンテキストの値を束ねたもの**である。

| 値 | 持っているコンテキスト |
| --- | --- |
| 社員番号・在籍期間 | `employee` |
| 労働時間・不足時間・年休日数・日数 | `attendance` |
| 月次勤怠の状態（除外の理由） | `approval` |
| 暦日区分・1 日の所定労働時間 | `workrule` |

`attendance` に置くことはできない。
[04 API設計書](../04_勤怠_月次清算/API設計書.md) は
**「社員番号・氏名・部署を返さない。それらは `employee` が所有する概念である」**
と決めている（[設計規約チェックリスト 3](../00_共通/設計規約チェックリスト.md)）。
出力の 1 行は社員番号で始まるので、`attendance` に置いた瞬間にこの規約を破る。
判断の経緯は [ADR 0007](../../05_ADR/0007_給与連携を新しい業務コンテキストにする.md)。

`payroll` は**どのコンテキストからも参照されない末端**である。
依存の向きは外へ出るだけなので、循環は生じない。

## 2. 出力する 1 行

```java
/** 給与計算システムへ渡す 1 行（1 社員 × 1 対象月）。 */
public record PayrollRow(
        EmployeeNumber employeeNumber,   // ① 名寄せの鍵。UUID は出さない
        YearMonth month,                 // ②
        DateRange period,                // ③ 暦月 ∩ 在籍期間（BR-05）。賃金計算期間ではない
        WorkingTimeSystemType system,    // ④
        int monthlyScheduledDays,        // ⑤ 暦月の所定労働日数（日額の分母）
        int scheduledDays,               // ⑥ 清算期間の所定労働日数（年休を引く前）
        int attendedDays,                // ⑦ 出勤日数（法定休日・所定休日の出勤を含む）
        int paidLeaveDays,               // ⑧ 年次有給休暇の取得日数
        int absentDays,                  // ⑨ 欠勤日数
        Duration workingTime,            // ⑩ 実労働時間
        Duration scheduledInsideTime,    // ⑪ 所定内労働時間（月給に含む）
        Duration beyondScheduledTime,    // ⑫ 所定超労働時間（1.0 倍の追加支払）
        Duration overtimeUpTo60Time,     // ⑬ 法定外残業 60 時間まで（+25%）
        Duration overtimeOver60Time,     // ⑭ 法定外残業 60 時間超（+50%）
        Duration legalHolidayTime,       // ⑮ 法定休日労働（+35%）
        Duration nightTime,              // ⑯ 深夜労働（+25%）
        Duration scheduledTotalTime,     // ⑰ 所定総労働時間（年休の日を除いた後）
        Duration shortageTime) {         // ⑱ 不足時間
```

#### 所定労働日数を 2 つ持つ

**日額の分母（⑤）と、所定総労働時間の根拠（⑥）は別の値である。**

月中入社・月中退職の月では清算期間が暦月より短くなる。
⑥ を日額の分母に使うと、暦月 21 日・清算期間 11 日の月で
`月給 ÷ 11` を引くことになり、控除が正しい `月給 ÷ 21` の **約 1.9 倍**になる。
労働の提供が無かった部分を超える控除であり、**労基法 24 条（賃金全額払い）に反する。**

しかも**⑤ は他のどの項目からも復元できない。**
③ は暦「日」の範囲であって所定労働日数ではなく、⑰ も清算期間ベースである。
給与側が自前で会社カレンダーを持たないかぎり作れないので、列として渡す。

**③ を賃金計算期間として使わせない。**
労基則 54 条 1 項 3 号の賃金計算期間は賃金規程が定めるもので、
3.6 の月末締めでは **② の暦月**である。③ は在籍期間で切った清算期間なので、
月中入社・退職者では一致しない。

### 2.1 基礎賃金の切り方と、割増の切り方は別である

**この設計でいちばん間違えやすい点である。**

| 切り方 | 何を分けるか | 列 |
| --- | --- | --- |
| **基礎賃金** | その時間の 1.0 倍が月給に含まれているか | ⑪（含まれる）/ ⑫（含まれない）|
| **割増**（労基法 37 条） | その時間に何 % を上乗せするか | ⑬ 25% / ⑭ 50% / ⑮ 35% / ⑯ 深夜 +25% |

**2 つは入れ子になっていない。** ⑬⑭⑮⑯ は⑪とも⑫とも重なる。

> **重なる例（第 1 版はここを間違えた）。**
> 所定総が法定総枠を上回る月に、対象労働時間が所定を 160 分**下回った**とする。
> 総枠は所定より小さいので、**所定に届いていないのに 115 分の時間外労働**が生じる
> （[04 ドメインモデル設計書](../04_勤怠_月次清算/ドメインモデル設計書.md) の「時間外と不足は同時に発生しない、は誤りだった」）。
>
> | | 値 |
> | --- | --- |
> | 実労働 ⑩ | 10,400 分 |
> | 所定総 ⑰ / 不足 ⑱ | 10,560 分 / 160 分 |
> | **所定内 ⑪** | **10,400 分**（すべて所定の内側）|
> | **所定超 ⑫** | **0 分** |
> | 法定外残業 ⑬ | 115 分 |
>
> 支払うのは `0.25 × 115` だけである。基礎賃金 1.0 は月給に含まれている。
>
> 第 1 版は「割増の付かない労働時間」を所定内と法定内残業へ割っていた。
> その式ではこの月の所定内が 10,285 分になり、
> 給与側が `実労働 − 所定内` を 1.0 倍の対象と読むと **115 分を二重に払う。**
> **⑬が正だから⑫も正になる、ということはない。**

### 2.2 ⑪⑫をどこで導くか

**`MonthlySettlement` の導出メソッドとして `attendance` に置く**（`payroll` では計算しない）。

```java
// attendance.domain.monthly.MonthlySettlement
/** 所定内労働時間。所定の範囲内で実際に働いた時間であり、月給に含まれている。 */
public Duration scheduledInsideTime() {
    return scheduledTotalTime.minus(shortageTime);
}

/** 所定超労働時間。通常の賃金 1.0 倍の追加支払が要る（割増の有無とは無関係）。 */
public Duration beyondScheduledTime() {
    return workingTime.minus(scheduledInsideTime());
}
```

**`所定総 − 不足時間` が「所定の範囲内で実際に働いた時間」になる理由。**
不足時間は制度によって数え方が違うが、どちらも
「所定総 − 実績（実績は所定で頭打ち）」の形をしている。

| 制度 | 不足時間 | 所定総 − 不足時間 |
| --- | --- | --- |
| 固定時間制 | `max(0, 所定総 − Σ min(その日の実労働, その日の所定))` | `min(所定総, Σ min(その日の実労働, その日の所定))` |
| フレックス | `max(0, 所定総 − 対象労働時間)` | `min(所定総, 対象労働時間)` |

法定休日には所定が無いので（`scheduledOn` が 0 を返す）、
**法定休日労働は必ず⑫に入る。** 1.0 + 0.35 が支払われる。

> **`max(0, …)` を落として読まない。**
> 年休を承認した日に出勤した月（[06](../06_年次有給休暇/ドメインモデル設計書.md) の警告が示す状態）では
> `Σ` が所定総を超えるので、⑪は `min` のほうで決まる。
> このとき⑫はその日のぶんだけ大きくなる。**社員に不利にならない側へ倒れる。**

> **`payroll` に式を置かない。** ⑪は不足時間の定義に依存しており、
> 不足時間の定義を持っているのは `attendance` である。
> 写すと、制度ごとの数え方を直したときに片方だけが古くなる（落とし穴 67）。

### 2.3 ⑬⑭の分割

```java
overtimeOver60Time  = settlement.overtimeOver60Time()   // 04 が既に持っている
overtimeUpTo60Time  = settlement.overtimeTime() − overtimeOver60Time
```

`overtimeOver60Time()` は `MonthlySettlement` の導出メソッドである（04 の 3.4）。
閾値（60 時間）は法定値なので `payroll` 側に定数を置かない（落とし穴 15）。

### 2.4 ⑯を合計に数えない

深夜は他の区分と**重なる属性**であり、労働時間を分割する区分ではない（BR-06）。
給与側は `単価 × 0.25 × ⑯` を別に足す（BR-18 の式）。

### 2.5 不変条件

| 検査 | なぜ置くか |
| --- | --- |
| `⑪ + ⑫ = ⑩` | 所定内と所定超は実労働を分割する |
| `⑬ + ⑭ + ⑮ ≤ ⑩` | 割増の区分は実労働の内側にある |
| `⑪ ≤ ⑰` | 所定内労働が所定総を超えることはない |
| `⑱ ≤ ⑰` | 不足は所定総に対する不足である |
| `⑯ ≤ ⑩` | 深夜は重複属性だが実労働の一部ではある（BR-06）|
| `⑧ + ⑨ ≤ ⑥` | 年休と欠勤は所定労働日のうちである |
| `⑥ ≤ ⑤` | 清算期間は暦月の部分集合なので、日額の分母のほうが必ず大きいか等しい |
| 日数・時間が負でない | — |

> **これらは本番の経路では働かない。**
> ⑩〜⑱はすべて 1 つの `MonthlySettlement` から導くので、
> 集約の側で既に成り立っている（`targetWorkingTime = 実労働 − 法定休日`、
> `時間外 ≤ 対象労働時間`）。**代入すれば恒真である。**
>
> それでも置くのは、`PayrollRow` を**手で組み立てた**ときに気づけるようにするためである
> （落とし穴 58 と同じ理由）。
> 「別の出どころから受け取っているから検査になる」とは書かない。事実に反する（落とし穴 117）。

> **`⑦ ≤ ⑥`（出勤日数 ≤ 所定労働日数）は置かない。**
> 法定休日・所定休日に出勤した日は⑦に数えるが⑥には入らないので、
> **⑦のほうが多い月は適法に存在する。**
> だから欠勤日数を `⑥ − ⑦` で導かせず、⑨として別に渡す
> （落とし穴 23・51）。

## 3. 対象の数え上げ

### 3.1 誰を数えるか

**対象月に 1 日でも在籍していた社員。**

| 決定 | 理由 |
| --- | --- |
| 月中退職者を含める | 最終月の給与は必ず支払われる。除くと**退職者の最終給与が出ない** |
| 月中入社者を含める | 同じ理由。清算期間は在籍期間との交差になる（③）|
| 対象月の初日時点の在籍で絞らない | 月中入社が落ちる。**在籍期間と対象月の重なり**で絞る |

> 落とし穴 63 と同型である。月末時点の在籍で絞ると、
> 月中退職（4/15）の社員が落ちるのに、退職日が月末（4/30）のテストでは通ってしまう。
> **月中退職の社員を必ず含めて検証する。**

**既存の `EmployeeRepository.findAll(asOf, includeRetired)` では足りない。**
基準日 1 点でしか絞れず、月中入社・月中退職のどちらかが必ず落ちる（落とし穴 75）。
`employee` に**期間の重なりで列挙する**経路を新設する（6 章）。

### 3.2 除外する理由

| 理由 | 何で判定するか | 人事が次に行うこと |
| --- | --- | --- |
| `NOT_SUBMITTED` | 打刻があり、状態が下書き | 本人に提出を促す |
| `NOT_APPROVED` | 状態が提出済み | 承認者に承認を促す |
| `NOT_CLOSED` | 状態が承認済み | 締める |
| `NOT_SUBMITTABLE` | 提出の事前条件を満たしていない | 打刻を訂正させる／規則を適用する |
| `NO_ATTENDANCE_RECORD` | **その月の打刻が 1 件も無い** | 休業か打刻漏れかを確かめる |
| `DUPLICATE_EMPLOYEE_NUMBER` | 同じ社員番号の社員が対象月に 2 人いる | 番号を割り当て直す |

**`NO_ATTENDANCE_RECORD` を「月次勤怠の行が無いこと」で判定しない。**
月次勤怠の行は提出時に初めて作られるので、
[05 ドメインモデル設計書](../05_申請承認と締め/ドメインモデル設計書.md) は
**行が無い月を「下書き相当」**と定めている（`MonthlyAttendanceService.stateOf` も `DRAFT` を返す）。
行の有無で分けると、**1 か月まるまる働いて提出していないだけの社員**に
「1 日も打刻が無い。休業か打刻漏れかを確かめる」という案内を返すことになる。
判定は**打刻という一次証拠の有無**で行う。

**`NOT_SUBMITTABLE` を一般の未提出と混ぜない。**
未退勤の勤務日が残っている社員・就業規則が未適用の社員は、
本人が提出しようとしても `requireCalculable` に拒否される
（[05 ドメインモデル設計書 2.3](../05_申請承認と締め/ドメインモデル設計書.md)）。
「本人に提出を促す」という**実行できない案内**を返すことになる（落とし穴 26 と同型）。

**`DUPLICATE_EMPLOYEE_NUMBER` は起こりうる。**
社員番号の一意制約は `WHERE retired_on IS NULL` の部分一意インデックスであり、
**退職者の番号は再利用できる**（[01 DB設計書](../01_社員・組織/DB設計書.md)）。
5/15 に退職した `E0042` と、5/16 に入社して同じ番号を割り当てられた社員は
**どちらも 5 月の在籍者**なので、同じ CSV に社員番号が重複する 2 行ができる。
給与側は社員番号で名寄せするので、**別人が同一人物になる。**

| 決定 | 理由 |
| --- | --- |
| **2 人とも除外する** | どちらを残しても、残したほうが「その番号の社員」として給与を受け取る |
| 例外にしない（依頼は成り立っている） | 他の 98 名の給与は出す。全件を止めると 1 件の番号衝突で給与処理が止まる |
| 番号の再利用そのものは禁じない | `employee` の決定（退職者の番号は再利用できる）を給与連携の都合で変えない。**衝突した月にだけ人事が割り当て直す** |

> `exported_by` に社員番号ではなく社員 ID を持たせているのは同じ理由である
> （[DB設計書 2.1](DB設計書.md)）。**同じ危険を CSV の鍵にも当てる。**

### 3.3 日数を数えるのは `attendance`

| 値 | 数え方 |
| --- | --- |
| ⑤ 暦月の所定労働日数 | **暦月**の所定労働日数。在籍期間で切らない |
| ⑥ 清算期間の所定労働日数 | 清算期間の所定労働日数（**年休を引く前**）|
| ⑦ 出勤日数 | 実労働が 1 分でもある勤務日の数（法定休日・所定休日の出勤を含む）|
| ⑨ 欠勤日数 | 所定労働日のうち、年休でもなく実労働が 1 分も無い日数 |

**`payroll` が会社カレンダーを引いて数え直さない。**
⑰（所定総労働時間）は `(⑥ − ⑧) × 1 日の所定`として `attendance` が計算しており、
`payroll` が別に数えると **⑰と⑥が食い違う**（落とし穴 67）。

**⑥を年休控除後にしない。**
給与側は日額で欠勤控除する。控除後の値を渡すと、
**年休を取った月ほど 1 日あたりの控除が大きくなる**
（所定 20 日・年休 5 日なら、月給 ÷ 20 ではなく月給 ÷ 15 が引かれる）。
⑰の根拠が要るので、年休控除後の日数は `⑥ − ⑧` で復元できるようにしておく。

#### 欠勤日数を引き算で導かない

```java
// してはならない
int absentDays = Math.max(0, scheduledDays - leaveDays - workedOnScheduledDays);
```

**年休を承認した日に出勤した月**（落とし穴 97）では、その日が
**年休の日数にも実労働のある日にも数えられる**ので、同じ日を 2 回引くことになる。
`Math.max(0, ...)` は負にならないようにするだけで、重なりを取り除かない。
結果として欠勤日数が 1 日少なく出て、⑨ を入力にした**欠勤控除が静かに漏れる。**

定義（所定労働日のうち、年休の日でも実労働のある日でもない日）をそのまま数える。

#### 清算期間は保存済みの月次清算から渡す

⑤〜⑨ は CSV を作るたびに数え直す。
このとき清算期間を `periodOf(employeeId, month)` で引き直すと、
**締めたあとに登録された退職日で期間が縮み、同じ出力の記録から出る CSV が変わる**
（落とし穴 122）。保存済みの `MonthlySettlement` が持つ清算期間を渡して固定する。

⑦⑨は状態機械の判定ではなく単純な件数なので、SQL で数えてよい。
落とし穴 69 が禁じているのは「未退勤か」のような**状態の判定**を SQL に写すことである。

## 4. 年間の所定（割増賃金の基礎額）

労基則 19 条 1 項 4 号は、月給の場合の割増賃金の基礎額を
**「1 年間における 1 か月平均所定労働時間数」**で除して求めると定める。

```java
public record AnnualScheduledHours(
        int fiscalYear,          // 年度（4 月 〜 翌 3 月）
        DateRange period,        // 数えた範囲
        int scheduledDays,       // 年間の所定労働日数
        Duration annualTotal,    // 年間の所定労働時間
        Duration monthlyAverage) // annualTotal ÷ 12（分未満切り捨て）
```

| 決定 | 理由 |
| --- | --- |
| **月次の CSV に入れない。年ごとの別表にする** | 全社員に共通の値であり、社員ごとの行に持たせると 100 行に同じ値が並ぶ。そもそも 1 か月ぶんの行から年間の値は出せない（CLAUDE.md 落とし穴 118）|
| 年休を差し引かない | 社員ごとの事情であり、基礎額は**会社の所定**で決まる |
| 在籍期間で切らない | 同じ理由。月中入社の社員がいるだけで値が割れてはならない |
| 年度は 4 月 〜 翌 3 月 | **賃金規程が定める 1 年に合わせる。** 3.6 が月末締めなので、賃金計算期間（暦月）を 12 個並べた 4/1〜3/31 と一致する。36 協定の年度（BR-12）と同じ区切りになるのは結果であって理由ではない（36 協定の起算日は協定当事者が定めるもので、分母とは制度上つながらない）|
| 年度は**労働月**で決める | 2027 年 3 月分を 4 月に出力しても年度は 2026。支払月で決めると、同じ労働に別の分母が当たる |
| **分未満は切り捨て** | 分母なので、大きくすると単価が下がる。切り上げると法定を下回る側へ倒れる |

### 4.1 「日数 × 1 日の所定」では求めない

この式は**「1 日の所定が年度を通じて一定」を暗黙に仮定している。**
就業規則は年度の途中で改定できる（版の有効期間は任意の日で切れる）ので、
10 月に 7 時間 45 分へ改定された年度では黙って過大な分母を返す。

**所定労働日ごとに、その日に有効な版の所定を足す。**

```java
for (LocalDate date : 年度の各日) {
    if (カレンダー.dayTypeOf(date) != WORKDAY) continue;
    total = total.plus(その日に有効な版.scheduledDailyWorkingTime());
}
```

`scheduledDailyWorkingTime()` は `WorkRule` が持つ（`switch` は 1 か所）。
**`payroll` にも `workrule.application` にも写さない**（落とし穴 67）。

> フレックスの `standardDailyWorkingTime` は<strong>日々の所定ではない</strong>。
> フレックスの所定は清算期間の総労働時間（労基法 32 条の 3）であり、
> この値はそれを算出するための**係数**である
> （[02 ドメインモデル設計書](../02_就業規則・カレンダー/ドメインモデル設計書.md)）。
> 年間の所定 = Σ（各清算期間の所定総）= 年間所定労働日数 × 係数 なので、
> 分母の算出に使ってよい。**日々の残業判定には使わない。**

### 4.2 所定が 1 つに定まらない年度は拒否する

要件 3.1 は全社員 1 日 8 時間と定めているが、**DB はそれを守っていない。**
所定は「法定の 8 時間を上限とする 1 分単位の値」であり、
7 時間 45 分の規則を登録できる。

労基則 19 条の分母は**その労働者の所定**である。
所定 7 時間 45 分の社員に 8 時間で計算した分母（163 時間 20 分）を当てると、
正しい分母（153 時間 7 分）より約 6.6% 大きく、**単価が 6.6% 低くなる。**
37 条の割増は下限なので、そのまま未払いになる。

| 決定 | 理由 |
| --- | --- |
| 年度に**適用されている系列**から集める | `findAll()` で全系列を舐めると、廃止済みの系列や 8 年前の版まで巻き込む。**一度でも違う所定の規則を作った会社は永久に出力できない** |
| **判定は日ごとに行う**（系列ごとに 1 年ぶんを足してから比べない）| 下記 |
| **同じ日**に所定の異なる規則が並んでいたら **422**（`multiple-scheduled-working-times`） | 静かに 1 つの値を返してはならない |
| 年度に適用が 1 つも無ければ **422**（`work-rule-not-in-use`） | 0 を返すと給与側がゼロ除算する |
| 所定労働日なのに適用が 1 つも無い日があれば **422**（`work-rule-not-applied-on`） | 0 時間として数えると年間の所定が過少に出る。導入初年度に必ず起こる |
| **適用されているのに版が無い**日があれば **422**（`work-rule-version-missing`） | 本当の隙間である。素通りさせると年間の所定が過少に出る |

#### 系列ごとに 1 年ぶんを足してはならない

系列の一覧だけを取り、**系列ごとに年度の全所定労働日について版を要求する**と、
「年度の途中で新設した系列」を隙間と誤診断する。

> 10 月からフレックス制度を導入した会社。新しい系列の版は 10/1 から始まる。
> 4 月〜9 月の所定労働日にその系列の版は無いが、これは**正常**である
> （その系列はまだ存在しなかった）。
> それでも `work-rule-version-missing` を投げると、
> **その年度のどの月も永久に出力できない。**
> 版を 4/1 まで遡って捏造する以外に手が無い。

4.2 の第 1 版は「廃止済みの系列を巻き込むと永久に出力できなくなる」ことを避けるために
系列を絞り込んだのに、**版の隙間の検査で同じ結果に戻していた**（落とし穴 131）。

日ごとに「その日に適用されている系列」だけを見る。副産物として、
**年度の途中で全社の所定を改定した年度**（4〜9 月 480 分・10〜3 月 465 分）も
正しく数えられる。

> **短時間勤務を入れるなら、この API は社員別または系列別になる。**
> 要件 3.1 は「所定労働時間が社員ごとに異なる場合、BR-04 と BR-05 を
> すべて社員単位に一般化する必要がある」と書いているが、
> **BR-18 の分母もその一般化の対象である。**

### 4.3 カレンダー未登録の年度を静かに返さない

`CompanyCalendar` は**未登録の日を所定労働日として扱う**
（登録漏れを休日と判定すると通常勤務に休日割増が付いて過払いになるため）。

したがって登録していない年度は所定労働日数が暦日数に近づく。

| 年度の状態 | 年間所定労働日数 | 1 か月平均 |
| --- | --- | --- |
| 正しく登録された年度 | 261 日 | 174 時間 00 分 |
| **4 月だけ登録した年度** | **357 日** | **238 時間 00 分**（単価が 27% 低い）|
| **まったく登録していない年度** | **365 日** | **243 時間 20 分**（単価が 33% 低い）|

**判定は「年度の全日が登録されていること」で行う。**

第 1 版は「その年度に法定休日が 1 日も登録されていないこと」としていたが、
**4 月だけ登録した年度は法定休日を 4 日持つので通過する。**
防ごうとした事故が、より起きやすい形ですり抜けていた。

**欠けている日そのものを集める。** 登録件数と日数の比較にしない。
`findByPeriod` が期間で絞っている事実に正しさが依存し、2 か所で保つことになる。

#### 全日登録を要求する以上、登録する手段が要る

1 日ずつの API しか無いと年度ぶんで 365 回叩くことになる。
[02 API設計書 3.2](../02_就業規則・カレンダー/API設計書.md) が定めていた
**一括設定 API（曜日の規則 + 個別の上書き）を実装した。**
委譲先が実際に扱えるかを確かめずに要求を書かない（落とし穴 94）。

### 4.4 年間の所定が法定の総枠を超えていないか（労基法 32 条）

登録に抜けが無くても、**中身が誤っている**ことはある。
全日を所定労働日として登録した年度は前の検査を通ってしまう。

| 年度の状態 | 年間の所定 | 上限（53 週 × 40 時間）| |
| --- | --- | --- | --- |
| 正しく登録された年度 | 2,088 時間 | 2,120 時間 | 通過 |
| 全日を所定労働日として登録 | 2,920 時間 | 2,120 時間 | **拒否** |

**週の数は切り上げる。**
32 条が定めるのは 1 週の上限であって年間の上限ではなく、
年度は週の整数倍ではない（365 日 = 52 週 + 1 日）。
`暦日数 ÷ 7` で数えると端数の週を数え落とし、
**土日を休みにしただけの正当なカレンダー**（261 日 × 8 時間 = 2,088 時間）が
切り捨てた総枠 2,085 時間 42 分を超えて拒否される（落とし穴 23・51）。

> **この上限は緩い。** 狙いは全日登録のような明らかな誤りを捕まえることであり、
> 1 か月ぶん（9 日）程度の登録漏れは通過する（月平均が 3.4% 過大）。
> 検出できない範囲があることを書かない検査は、守られていると誤読される
> （落とし穴 85・87）。抜けの検出は 4.3 が担う。

### 4.5 出力に使った分母は動かせない

年度の所定は**年度全体**から決まる。
締め済みの月のカレンダーは変えられないが（[02](../02_就業規則・カレンダー/API設計書.md)）、
**同じ年度のまだ来ていない月は変えられる。**

4 月分の給与を払ったあとに 12 月の休日を 1 日増やすと年度の分母が変わり、
**既に払った割増賃金の単価が事後的に足りなくなる。**
37 条の割増は下限なので、下回った月には差額の支払義務が残る。

| 決定 | 理由 |
| --- | --- |
| **分母を動かす変更を拒む**（`fiscal-year-used-by-payroll`・409） | 誰も気づけないまま起こるのが問題の本体なので、変更の側で止める |
| 拒むのは**分母が動く変更だけ**である | 下記 |
| 対象は**カレンダーだけではない**。就業規則の適用にも当てる | 年間の所定は「所定労働日 × その日に適用されている規則の所定」なので、適用を変えても動く |
| **1 行も出なかった記録は分母を凍結しない** | 下記 |
| ポートは `shared.domain.PayrollExportQuery`、実装は `payroll/infrastructure` | `workrule → payroll → workrule` の循環を作らない（ADR 0004）|
| 出力の記録に**分母の導出元**（年度・年間の所定労働日数・年間の所定労働時間）を残す | 月平均 10,440 分だけでは、261 日 × 480 分から出たのかを後から言えない |

#### 「出力したか」ではなく「分母が動くか」で判定する

出力の有無だけで拒むと、次の 2 つが同時に起こる。

| 起こること | 具体例 |
| --- | --- |
| 分母を**動かさない**変更まで止まる | 法定休日 → 所定休日の付け替え、名称の訂正。所定労働日数は変わらないのに 409 になり、**BR-07 の 35% 判定の誤りを年度いっぱい直せない** |
| 分母を**動かす**変更が素通りする | 就業規則の適用・改定。カレンダーだけを見ていると検査の外にある |

**書き込んだあとに年間の所定を数え直し、記録した値と突き合わせる。**
例外が飛べばトランザクションごと巻き戻る。
「変更したらどうなるか」を前もって組み立てると、数え方の実装が 2 か所になる（落とし穴 67）。

数え直した結果が**求められなくなった**場合（所定が割れた、など）も拒否する。
動いたかどうか以前の問題である。

#### 1 行も出なかった記録は凍結しない

`export` は誰も締めていなくても記録を作る（全員が理由つきで除外される）。
記録の有無だけで凍結すると、**人事が動作確認で 1 回叩いただけで、
その年度の 12 月・1 月のカレンダーを二度と直せなくなる。**
記録の削除 API は無いので、回復する手段もない。

全員が除外された記録は**誰にも賃金を払っていない**ので、
その分母が事後的に変わっても損害が生じない。
凍結の契機は「**行が出た**記録がその年度にあること」に限る。

## 5. 締め済みの値だけを読む

| 決定 | 理由 |
| --- | --- |
| **保存済みの `MonthlySettlement` を読む。出力時に計算し直さない** | 計算し直すと、会社カレンダーの過去分が変わったときに同じ月の CSV が変わる |
| 締め済みでない社員は読まない | 締めていない月の値は後から変わる（BR-10）|
| 締め済みの月に誤りが見つかっても直せない | BR-10 が締め済みからの遷移を持たない。給与側で調整する |

### 5.1 行の値が動かないことと、行の集合が動かないことは別である

CSV の本文は保存しない（DB設計書 1）。
**その代わり、対象社員の集合を記録に残す。**

保存せずに毎回作り直すと、
**出力の記録を作ったあとに人事が残りの社員を締めた**とき、
同じ記録から取得した CSV の行数が増える。
記録の「97 名」と CSV の 100 行が食い違い、
**記録が「何を出したか」を指さなくなる。**

| 決定 | 理由 |
| --- | --- |
| 出力の記録に**対象社員と除外理由を行として残す** | 集合を固定する。あとから取得しても同じ社員が並ぶ |
| 行数は**残した行から数える。列として持たない** | 2 か所に持つと食い違う（落とし穴 39）|
| 値そのものは保存しない | 締め済みの月次清算は動かないので、社員が固定されていれば内容も固定される |
