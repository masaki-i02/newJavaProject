## 1. このコンテキストの責務

社員と組織を管理し、**「ある日付において、誰がどの部署に所属し、その部署の長は誰か」** に答える。

勤怠の集計そのものには関与しない。ただし承認フロー（`approval`）が承認者を決めるために
このコンテキストへ問い合わせるため、**日付を指定した問い合わせに答えられること** が要件になる。

## 2. モデル

<sub>図のソース: [`diagrams/ドメインモデル.mmd`](diagrams/ドメインモデル.mmd)</sub>

### 2.1 値オブジェクト

| 型 | 表現するもの | 不変条件 |
| --- | --- | --- |
| `EmployeeId` | 社員の識別子 | UUID が非 null |
| `DepartmentId` | 部署の識別子 | UUID が非 null |
| `EmployeeNumber` | 社員番号 | 英数字 1〜20 文字 |
| `Email` | メールアドレス | `@` を含む。比較は小文字で行う |
| `DateRange` | 日付の期間（`shared`） | `from < toExclusive`。`toExclusive` が null なら無期限 |

**識別子を `UUID` の生値で持ち回らない。**
`findById(UUID)` は社員 ID でも部署 ID でも通ってしまうが、
`findById(EmployeeId)` なら取り違えがコンパイルエラーになるため。

### 2.2 エンティティ

#### Employee

```java
public record Employee(
        EmployeeId id,
        EmployeeNumber number,
        String name,
        Email email,
        EmploymentType employmentType,
        LocalDate hiredOn,
        LocalDate retiredOn,      // null は在籍中
        Set<Role> roles) {

    public Employee {
        // 退職日が入社日より前になることはありえない
        if (retiredOn != null && retiredOn.isBefore(hiredOn)) { ... }
        roles = Set.copyOf(roles);
    }

    /** 指定日に在籍しているか。 */
    public boolean isActiveOn(LocalDate date) {
        return !date.isBefore(hiredOn) && (retiredOn == null || !date.isAfter(retiredOn));
    }
}
```

**退職しても行を消さない。** 過去の勤怠・承認履歴が社員を参照するため、
`retiredOn` を立てることで表現する。

#### Department

```java
public record Department(
        DepartmentId id,
        DepartmentCode code,
        String name,
        DepartmentId parentId,     // null はルート
        LocalDate abolishedOn) {

    public boolean isRoot() { return parentId == null; }
    public boolean isActiveOn(LocalDate date) { ... }
}
```

部署そのものは有効期間を持たない。組織改編の履歴管理は要件に含まれないため
（[要件定義書 2.3](../../01_要件定義/要件定義書.md#23-システム化の範囲)）、
廃止日のみを持つ。

#### Assignment（所属）

```java
public record Assignment(EmployeeId employeeId, DepartmentId departmentId, DateRange period) { }
```

**社員の所属は有効期間を持つ。** BR-11 が「対象月の初日時点の所属部署」を要求するため、
異動しても過去の所属が辿れなければならない。

兼務は扱わない（[要件定義書](../../01_要件定義/要件定義書.md) の合意）。
したがって **ある社員のある日付における所属は必ず 0 件か 1 件** であり、
これは DB の排他制約で保証する（DB設計書 3.5）。

#### Managership（部署長）

```java
public record Managership(DepartmentId departmentId, EmployeeId employeeId, DateRange period) { }
```

**部署長も有効期間を持つ。** 部署長は交代するため、過去月の承認者を判定するには
その時点の部署長を知る必要がある。

> 所属（誰がどの部署にいたか）だけを履歴化して部署長を現在の値で持つと、
> 「4 月分を 6 月に承認するとき、5 月に交代した新しい部署長が承認者になる」
> という誤りが起きる。両方を履歴化して初めて BR-11 が正しく実装できる。

### 2.3 ドメインサービス

`OrganizationChart` は複数のエンティティにまたがる判断を担う。
1 つの record に置くと不自然になるため、ドメインサービスとして切り出す。

```java
public interface OrganizationChart {
    /** 指定日に社員が所属していた部署。 */
    Optional<Department> departmentOf(EmployeeId employeeId, LocalDate date);

    /** 指定日における承認者。BR-11 を実装する。 */
    Optional<EmployeeId> managerOf(EmployeeId employeeId, LocalDate date);

    /** 部署から根までの祖先を近い順に返す。 */
    List<Department> ancestorsOf(DepartmentId departmentId);
}
```

## 3. 承認者の導出（BR-11）

![組織階層と承認者の導出](images/組織階層と承認者の導出.png)

<sub>図のソース: [`diagrams/組織階層と承認者の導出.mmd`](diagrams/組織階層と承認者の導出.mmd)</sub>

### 3.1 手順

1. 対象月の初日時点で有効な `Assignment` を引き、所属部署を得る
2. その部署の、同時点で有効な `Managership` を引く
3. **部署長が設定されていなければ親部署へ遡り、見つかるまで繰り返す**
4. 根まで遡っても見つからなければ「承認者なし」を返す

```java
public Optional<EmployeeId> managerOf(EmployeeId employeeId, LocalDate date) {
    return assignments.findEffective(employeeId, date)
            .flatMap(assignment -> findManagerUpwards(assignment.departmentId(), date));
}

private Optional<EmployeeId> findManagerUpwards(DepartmentId departmentId, LocalDate date) {
    for (Department department : ancestorsOfIncludingSelf(departmentId)) {
        Optional<EmployeeId> manager = managerships.findEffective(department.id(), date);
        if (manager.isPresent()) {
            return manager;
        }
    }
    return Optional.empty();
}
```

### 3.2 境界条件

| 状況 | 振る舞い | 理由 |
| --- | --- | --- |
| 承認者が本人と一致する（部署長自身の勤怠） | 承認者なしとし、親部署の長へ遡る | 自己承認を許すと承認の意味が失われる |
| 根まで遡っても部署長がいない | 承認者なしを返す | 呼び出し側（`approval`）が「承認者未設定」として扱い、人事へ通知する |
| 対象日に所属がない（入社前・退職後） | 空を返す | 例外にしない。過去データの照会で正常に起こりうるため |
| 承認者が対象日に退職済み | 承認者なしとし、親部署の長へ遡る | 退職者は承認できない |

> 自己承認の除外は BR-11 に明記されていない。**要件定義書へのフィードバックが必要**
> （未決事項として記録し、確認のうえ BR-11 に追記する）。

## 4. ポート（永続化の窓口）

`domain` パッケージにインターフェースとして宣言し、`infrastructure` が実装する。

```java
public interface EmployeeRepository {
    Optional<Employee> findById(EmployeeId id);
    List<Employee> findActiveOn(LocalDate date);
    void save(Employee employee);
}

public interface DepartmentRepository {
    Optional<Department> findById(DepartmentId id);
    List<Department> findAll();
    /** 指定部署から根までの祖先を近い順に返す（再帰 CTE で取得する）。 */
    List<Department> findAncestors(DepartmentId departmentId);
    /** 指定部署の配下すべてを返す。 */
    List<Department> findDescendants(DepartmentId departmentId);
}

public interface AssignmentRepository {
    /** 有効期間の重複は DB が禁止しているため、結果は高々 1 件。 */
    Optional<Assignment> findEffective(EmployeeId employeeId, LocalDate date);
    List<Assignment> findHistory(EmployeeId employeeId);
    void save(Assignment assignment);
}

public interface ManagershipRepository {
    Optional<EmployeeId> findEffective(DepartmentId departmentId, LocalDate date);
    void save(Managership managership);
}
```

`findEffective` が `Optional` を返せるのは、**有効期間の重複を DB の排他制約が禁止している**
からである。アプリケーション側で「複数見つかったらどうするか」を考えなくてよい。

## 5. 単体テストの観点

| ID | 観点 | 期待 |
| --- | --- | --- |
| UT-EMP-01 | `isActiveOn` の境界 | 入社日当日は在籍、入社日前日は非在籍、退職日当日は在籍、翌日は非在籍 |
| UT-EMP-02 | 退職日 < 入社日 | 生成時に例外 |
| UT-ORG-01 | 所属部署に部署長がいる | その部署長を返す |
| UT-ORG-02 | 所属部署に部署長がいない | 親部署の長を返す |
| UT-ORG-03 | 部署長が本人 | 親部署の長を返す |
| UT-ORG-04 | 根まで部署長がいない | 空を返す |
| UT-ORG-05 | 異動を挟む | 対象日によって異なる部署長を返す |
| UT-ORG-06 | 部署長が交代している | 対象日時点の部署長を返す |
| UT-ORG-07 | 対象日に所属なし | 空を返す（例外にしない） |

**UT-ORG-05 と UT-ORG-06 が本コンテキストの中心。**
所属と部署長の双方を履歴化した意味は、この 2 つのテストが通ることで示される。
