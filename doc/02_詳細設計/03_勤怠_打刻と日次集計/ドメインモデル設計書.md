## 1. このコンテキストの責務

打刻を記録し、**1 日分の労働時間を割増区分ごとに集計する。**

日単位で確定するのは、深夜・法定休日、および **固定時間制の** 残業判定である。
フレックスタイム制の残業は清算期間の総労働時間で決まるため、
日次では区分せず [04_勤怠_月次清算](../04_勤怠_月次清算/) に委ねる（BR-05）。

### 1.1 他コンテキストへの依存

| 参照するもの | 置き場所 | 用途 |
| --- | --- | --- |
| `EmployeeId` / `TimeRange` / `DateRange` | `shared.domain` | 共有語彙 |
| `PremiumType` | `shared.domain` | 割増区分。`workrule` も使うため `attendance` に置くと循環する |
| `MonthClosureQuery` | `shared.domain`（実装は `approval`） | 締め済みの月への追記を拒否する |
| `WorkRule` / `DayType` | `workrule.domain` | 計算パラメータ。依存図に `attendance → workrule` の辺がある |

**`approval` の型は参照しない。** 締め判定は `shared` のポート経由で行う
（[アーキテクチャ設計書](../00_共通/アーキテクチャ設計書.md)）。

### 2.1 TimeClockEvent — 打刻イベント

```java
public sealed interface TimeClockEvent
        permits TimeClockEvent.ClockIn,
                TimeClockEvent.ClockOut,
                TimeClockEvent.BreakStart,
                TimeClockEvent.BreakEnd {

    LocalDateTime occurredAt();

    record ClockIn(LocalDateTime occurredAt) implements TimeClockEvent {}
    record ClockOut(LocalDateTime occurredAt) implements TimeClockEvent {}
    record BreakStart(LocalDateTime occurredAt) implements TimeClockEvent {}
    record BreakEnd(LocalDateTime occurredAt) implements TimeClockEvent {}
}

/** 打刻の発生元。 */
public enum ClockSource {
    WEB,          // 本人が画面から打刻した
    CORRECTION;   // 訂正申請の承認により追記された（3 章）
}
```

**種別を enum のフィールドではなく型で表現する。**
`enum EventType` を持つ 1 つのクラスにすると、状態遷移を書く `switch` に
`default` 句が必要になり、種別を増やしたときのハンドリング漏れが実行時まで分からない。
`sealed interface` なら網羅性がコンパイラに保証される。

> **`ClockSource` を要件に無い値で増やさない。** モバイルアプリ・IC カード・一括取込は
> 要件定義書のどこにも無い。必要になったら要件を先に改訂する
> （[設計規約チェックリスト 1](../00_共通/設計規約チェックリスト.md)）。

### 2.2 TimeClockSequence — 打刻の状態機械（BR-02）

![打刻の状態機械](images/打刻の状態機械.png)

<sub>図のソース: [`diagrams/打刻の状態機械.mmd`](diagrams/打刻の状態機械.mmd)</sub>

```java
public List<TimeRange> toWorkedRanges() {
    List<TimeRange> ranges = new ArrayList<>();
    Status status = Status.NOT_STARTED;
    LocalDateTime segmentStart = null;

    for (TimeClockEvent event : events) {
        switch (event) {
            case ClockIn in -> {
                requireStatus(status, NOT_STARTED, "出勤", in.occurredAt());
                status = WORKING;
                segmentStart = floorToMinute(in.occurredAt());     // 労働の開始側は切り捨て
            }
            case BreakStart bs -> {
                requireStatus(status, WORKING, "休憩開始", bs.occurredAt());
                addRange(ranges, segmentStart, ceilToMinute(bs.occurredAt()));  // 終了側は切り上げ
                status = ON_BREAK;
            }
            case BreakEnd be -> {
                requireStatus(status, ON_BREAK, "休憩終了", be.occurredAt());
                status = WORKING;
                segmentStart = floorToMinute(be.occurredAt());
            }
            case ClockOut out -> {
                requireStatus(status, WORKING, "退勤", out.occurredAt());
                addRange(ranges, segmentStart, ceilToMinute(out.occurredAt()));
                status = FINISHED;
            }
        }
        // default 句が無い。打刻種別を追加した瞬間にコンパイルエラーになる
    }
    // ★ ループを抜けた時点で退勤していなければ、最後の区間が黙って落ちている。
    //   ただし打刻が 1 件も無い日は欠勤であって異常ではないので、例外にしない
    if (status != FINISHED && !events.isEmpty()) {
        throw new InvalidTimeClockSequenceException("退勤打刻がないため労働時間を確定できません");
    }
    return ranges;
}
```

| メソッド | 用途 |
| --- | --- |
| `validateTransitions()` | 遷移の妥当性だけを検査する。**退勤前の途中状態も許容する** |
| `isClosed()` | 退勤まで完了しているか。日次勤怠を計算できるかの判定 |
| `toWorkedRanges()` | 実労働区間へ変換する。**未完了なら例外**（末尾の `requireStatus`） |

**検査と変換を分けるのは、打刻を受け付ける時点ではまだ勤務が終わっていないため。**
「出勤打刻を 2 回した」は即座に拒否したいが、「まだ退勤していない」は正常な状態である。

#### 秒を分へそろえる（BR-01）

打刻は秒まで記録するが、集計単位は分である。
**端点を分へそろえる向きは、常に労働時間が長くなる側とする**（要件定義書 BR-01）。

| 端点 | 変換 | 例 |
| --- | --- | --- |
| 労働の開始（出勤・休憩終了） | `floorToMinute`（切り捨て） | 9:00:30 → 9:00 |
| 労働の終了（退勤・休憩開始） | `ceilToMinute`（切り上げ） | 18:00:30 → 18:01 |

**変換は `toWorkedRanges()` の中で 1 回だけ行う。**
以降の分割点（深夜帯・暦日境界・累積 8 時間）はすべて分単位なので、
細切れにしても秒が再び現れることはない。

> **区間ごとに分へ丸めてはいけない。**
> 30 分 30 秒の区間を 2 つに分けてそれぞれ丸めると、合計が 61 分になる。
> 内訳の合計が実労働時間と一致しなくなり、2.8 の不変条件が壊れる。

#### 境界条件

| 状況 | 振る舞い | 理由 |
| --- | --- | --- |
| 長さ 0 の区間（出勤と同時に休憩開始） | 区間として記録しない | 労働実績として意味を持たないため |
| 分へそろえた結果、長さ 0 になる区間 | 記録しない | 同上。開始が切り捨て・終了が切り上げなので、逆転はしない |
| 退勤打刻が無いまま計算を要求 | 例外 | 労働時間が確定しないため |
| 打刻が 1 件も無い | 空の結果（欠勤） | 例外にしない。休日や欠勤で正常に起こりうる |
| 出勤打刻が無いまま退勤打刻 | 例外。ただし打刻自体は記録する（4 章） | 証拠を捨てない |

### 2.3 TimeRange と WorkSlice

```java
/** 半開区間 [start, end)。区間の切り貼りを型に閉じ込める。 */
public record TimeRange(LocalDateTime start, LocalDateTime end) {
    public TimeRange {
        if (!start.isBefore(end)) { throw new IllegalArgumentException(...); }
        if (start.getSecond() != 0 || start.getNano() != 0
                || end.getSecond() != 0 || end.getNano() != 0) {
            throw new IllegalArgumentException("労働区間の端点は分精度である必要があります");
        }
    }
    public Optional<TimeRange> intersect(TimeRange other) { ... }
    /** instant が区間の内側なら 2 つに分ける。端点なら分けない（長さ 0 を作らない）。 */
    public List<TimeRange> splitAt(LocalDateTime instant) { ... }
}

/** 割増属性が確定した労働区間の最小単位。 */
public record WorkSlice(TimeRange range, Set<PremiumType> premiums) { }
```

`TimeRange` は `shared` に置く。月次清算でも使うため。

**すべて半開区間。** 22:00 ちょうどは深夜帯に含み、05:00 ちょうどは含まない。
`splitAt` を区間の端点で呼んでも長さ 0 の区間は生まれない。

**勤怠計算は「1 本の労働区間を、割増の切り替わり点でひたすら細切れにしていく」処理として
表現できる。** `WorkSlice` がその細切れ 1 つを表す。

### 2.4 勤務日と暦日（BR-03 / BR-07）

**この 2 つは別のものである。混同すると割増を取りこぼす。**

| 概念 | 意味 | 使いどころ |
| --- | --- | --- |
| **勤務日**（`workDate`） | 労働時間を通算する先。日をまたいでも出勤日に寄せる（BR-03） | 集計の帰属先。締めの単位 |
| **暦日** | 実際の 0:00 – 24:00 | **法定休日労働の判定**（昭 63.1.1 基発 1 号） |

土曜 22:00 出勤 → 日曜 06:00 退勤を考える。

```
勤務日 = 土曜（BR-03）
暦日   = 土曜 22:00–24:00 ｜ 日曜 00:00–06:00
                              ↑ ここが法定休日労働（35%）
```

**勤務日の暦日区分を全区間に適用してはいけない。**
そうすると日曜 0:00–6:00 の 35% が付かず、賃金の不払いになる。
逆に日曜 22:00 出勤 → 月曜 06:00 退勤では、
月曜分まで法定休日労働として 35% を付けてしまう（36 協定の集計も誤る）。

> 第 1 版はこの区別をしておらず、`day_type` 1 つで全区間の属性を決めていた。
> **区間の分割点として暦日境界を加える**ことで解決する（2.6）。

### 2.5 PremiumType — 割増区分（BR-04 / BR-06 / BR-07）

`shared.domain` に置く。`workrule` の `PremiumRates.multiplierFor` も使うため、
`attendance` に置くと `workrule → attendance` の依存が生まれて循環する。

```java
public enum PremiumType {
    OVERTIME_WITHIN_STATUTORY,   // 法定内残業。所定超だが法定内。割増の支払義務なし
    OVERTIME_BEYOND_STATUTORY,   // 法定外残業。25% 以上
    NIGHT,                       // 深夜。25% 以上
    LEGAL_HOLIDAY;               // 法定休日労働。35% 以上

    /**
     * 実労働時間を排他的に分割する区分か。
     * NIGHT だけは他に重ねて付く属性であり、合計には数えない。
     */
    public boolean partitionsWorkingTime() { return this != NIGHT; }
}
```

> **ここが本システムで最も間違えやすい箇所。**
> 深夜は「所定内かつ深夜」「法定外残業かつ深夜」のように **他の区分に重なる属性** であり、
> 労働時間を分割する区分ではない。この区別を型に持たせないと、
> 「深夜だけが付いた所定内の区間」をどの区分にも数え損ねる。
> 実際にこの誤りは、集計値の合計が実労働時間と一致しないという形で現れる（2.8 参照）。

`partitionsWorkingTime()` が真になるのは **`NIGHT` 以外の 3 つ**である。
どの排他区分も付かない区間が「基本時間」になり、4 つ目の排他バケツとして扱う。

### 2.6 AttendanceRule — 割増を付与する規則

```java
public sealed interface AttendanceRule
        permits CalendarDayBoundaryRule, NightWorkRule,
                LegalHolidayWorkRule, DailyOvertimeRule {

    /** 区間リストに規則を適用する。入力は時系列順である前提。 */
    List<WorkSlice> apply(List<WorkSlice> slices);
}
```

各規則は「区間リストを受け取り、必要に応じて分割・属性付与した区間リストを返す」純関数である。
合成できるため、適用する規則を差し替えるだけで計算内容が変わる。

| 規則 | 役割 | 対応要件 |
| --- | --- | --- |
| `CalendarDayBoundaryRule` | **暦日境界（0:00）で分割する。属性は付けない** | BR-03 / BR-07 |
| `NightWorkRule` | 深夜帯の境界で分割し `NIGHT` を付与 | BR-06 |
| `LegalHolidayWorkRule` | **その区間が属する暦日**が法定休日なら `LEGAL_HOLIDAY` を付与 | BR-07 |
| `DailyOvertimeRule` | 累積労働時間の境界で分割し残業区分を付与 | BR-04 |

#### 適用の順序

順序に意味がある。**分割する規則を先に、属性を付ける規則を後に適用する。**

```
① CalendarDayBoundaryRule   暦日で切る
② NightWorkRule             深夜帯で切り、NIGHT を付ける
③ LegalHolidayWorkRule      暦日が法定休日の区間に LEGAL_HOLIDAY を付ける
④ DailyOvertimeRule         残りの区間を累積で残業判定する
```

`DailyOvertimeRule` の累積は **`LEGAL_HOLIDAY` が付いた区間を数えない。**
法定休日労働は時間外労働に算入しないため（労基法 36 条）。
数えてしまうと、土曜深夜から日曜にかけて働いた社員の
「日曜分」が時間外にも法定休日にも二重に計上される。

### 2.7 計算パイプライン

![計算パイプライン](images/計算パイプライン.png)

<sub>図のソース: [`diagrams/計算パイプライン.mmd`](diagrams/計算パイプライン.mmd)</sub>

適用する規則は **労働時間制度**で決まり、残業判定の基準は **勤務日の区分**で決まる。

```java
List<AttendanceRule> rulesFor(WorkRule workRule, DayType workDayType) {
    var boundary = new CalendarDayBoundaryRule();
    var night    = new NightWorkRule(workRule.nightWindow());
    var holiday  = new LegalHolidayWorkRule(calendar);   // 暦日ごとに区分を引く

    return switch (workRule.workingTimeSystem()) {
        // 固定時間制: 日次で残業が確定する
        case FixedTimeSystem fixed -> List.of(
                boundary, night, holiday,
                new DailyOvertimeRule(scheduledFor(workDayType, fixed),
                                      workRule.statutoryDailyWorkingTime()));

        // フレックス: 日々の所定が無いので日次では残業を判定しない（BR-05）
        case FlextimeSystem flex -> List.of(boundary, night, holiday);
    };
    // default 句を書かない。制度を追加した瞬間にここがコンパイルエラーになる
}

/** その勤務日の所定労働時間。1 つの勤務日に所定は 1 つしかない。 */
private static Duration scheduledFor(DayType workDayType, FixedTimeSystem fixed) {
    return switch (workDayType) {
        case WORKDAY -> fixed.scheduledWorkingTime();
        // 所定休日・法定休日は所定労働時間 0 として扱う（BR-07）
        case NON_LEGAL_HOLIDAY, LEGAL_HOLIDAY -> Duration.ZERO;
    };
}
```

| 勤務日の区分 | 所定労働時間として扱う値 | 結果 |
| --- | --- | --- |
| 所定労働日 | 就業規則の所定労働時間 | 所定超・法定内なら法定内残業、法定超なら法定外残業 |
| 所定休日 | **0** | 8 時間までは法定内残業、超過分は法定外残業 |
| 法定休日 | **0** | 法定休日の暦日の区間は `LEGAL_HOLIDAY` が付き、累積の対象外。翌暦日へ及んだ分は法定内残業から始まる |

#### 所定労働時間は「勤務日」で決まる。「区間の暦日」ではない

第 1 版はこの表を「その区間の暦日」で引く形にしていた。**それでは定義できない。**

`DailyOvertimeRule` は累積労働時間で区分を決める。
累積の閾値を区間ごとに変えると、「累積 480 分」が何を指すのかが区間ごとに揺れる。
1 つの勤務日に所定は 1 つしかない。

**暦日が効くのは法定休日労働の判定だけである**（ADR 0005）。
2 つの分岐を混ぜないことが、フレックスに日次の残業を付けた誤りの再発を防ぐ
（CLAUDE.md 落とし穴 22）。

> **第 1 版は `switch (dayType)` だけで分岐しており、フレックス社員にも
> 日次の残業を付けていた。** BR-05 が定める「日々 8 時間を超えても、
> それ自体では時間外労働にならない」に反し、
> [就業規則 2.1](../02_就業規則・カレンダー/ドメインモデル設計書.md) の
> `case FlextimeSystem flex -> Duration.ZERO` とも矛盾していた。

#### 分割の具体例

![区間分割の例](images/区間分割の例.png)

<sub>図のソース: [`diagrams/区間分割の例.mmd`](diagrams/区間分割の例.mmd)</sub>

固定時間制・所定 8 時間・4/7（所定労働日）13:00 出勤 → 4/8 03:00 退勤、休憩 60 分。

| 区間 | 長さ | 暦日 | 割増属性 | 倍率 |
| --- | --- | --- | --- | --- |
| 13:00 – 18:00 | 300 分 | 4/7 所定労働日 | （なし・基本時間） | 1.00 |
| 19:00 – 22:00 | 180 分 | 4/7 所定労働日 | （なし・基本時間） | 1.00 |
| 22:00 – 24:00 | 120 分 | 4/7 所定労働日 | `NIGHT` + `OVERTIME_BEYOND_STATUTORY` | 1.50 |
| 00:00 – 03:00 | 180 分 | 4/8 所定労働日 | `NIGHT` + `OVERTIME_BEYOND_STATUTORY` | 1.50 |

実労働 780 分（13 時間）、休憩 60 分。基本時間 480 分、法定外残業 300 分、深夜 300 分。
**深夜 300 分は法定外残業 300 分と完全に重なっており、二重に足してはならない。**

暦日境界で 22:00–03:00 が 2 本に割れているが、
どちらも 4/7 が所定労働日なので結果は変わらない。
**4/8 が法定休日なら、00:00–03:00 だけが `LEGAL_HOLIDAY` になる。**

### 2.8 DailyAttendance — 集計結果

```java
public record DailyAttendance(
        LocalDate workDate,
        DayType dayType,                    // 勤務日の暦日区分。表示用（2.4）
        WorkingTimeSystemType workingTimeSystem,   // FIXED / FLEX
        List<WorkSlice> slices,             // 内訳。なぜこの結果かを説明するために保持する
        Duration workingTime,
        Duration breakTime,
        Duration baseTime,                  // どの排他区分も付かない時間
        Duration overtimeWithinStatutoryTime,
        Duration overtimeBeyondStatutoryTime,
        Duration nightTime,
        Duration legalHolidayTime) {

    public DailyAttendance {
        // ★ 排他的な 4 区分の合計は必ず実労働時間に一致する。深夜は重ね掛けなので含めない
        Duration breakdown = baseTime
                .plus(overtimeWithinStatutoryTime)
                .plus(overtimeBeyondStatutoryTime)
                .plus(legalHolidayTime);
        if (!breakdown.equals(workingTime)) {
            throw new IllegalStateException("内訳の合計が実労働時間と一致しません: ...");
        }
        // ★ 集計値は slices から再集計した値と一致しなければならない
        if (!recalculateFrom(slices).equals(this.totals())) {
            throw new IllegalStateException("集計値が内訳（slices）と一致しません: ...");
        }
        // ★ フレックスは日次で残業を判定しない（BR-05）
        if (workingTimeSystem == FLEX
                && !(overtimeWithinStatutoryTime.isZero()
                     && overtimeBeyondStatutoryTime.isZero())) {
            throw new IllegalStateException("フレックスに日次の残業を計上しています: ...");
        }
        if (nightTime.compareTo(workingTime) > 0) {
            throw new IllegalStateException("深夜労働時間が実労働時間を超えています: ...");
        }
    }
}
```

**この不変条件が集計ロジックの誤りを検出する。**
`daily_attendances` テーブルの CHECK 制約と対になっており、
DB へ到達する前に単体テストで落ちる。

#### `baseTime` の意味は制度で変わる

| 制度 | `baseTime` の意味 |
| --- | --- |
| `FIXED` | **所定内労働時間。** 日次で残業まで確定している |
| `FLEX` | **月次清算に委ねる労働時間。** 日次では区分しない（BR-05） |

「所定内」という名前にしないのは、**フレックスには日々の所定が無い**ためである。
制度が読み取れるよう `workingTimeSystem` を持たせ、
不変条件と DB の CHECK で「FLEX なら残業は 0」を守る。

集計値だけでなく `slices`（内訳）も保持する。
労務の問い合わせでは「なぜこの残業時間なのか」の提示が必須であり、
集計値だけでは答えられないため。
**両者が食い違わないことを compact constructor で検証する。**

## 3. 打刻の訂正（BR-09）

**打刻は追記のみ。登録済みのレコードを更新・削除しない。**
訂正は取消の行を積むことで表現する。

```
① 09:00 出勤          （ENTRY）
② 18:00 退勤          （ENTRY）
③ ②を取り消す         （REVOCATION → ②を参照）
④ 19:00 退勤          （ENTRY）
```

有効な打刻は「取り消されていない ENTRY」であり、上の例では ① と ④ になる。

| 決定 | 理由 |
| --- | --- |
| 元の打刻を残す | 打刻は労働時間の一次証拠。労務トラブル時に「元は何時だったか」を提示する必要がある |
| 訂正の**申請と承認**は `approval` が担う | 本コンテキストは承認済みの結果を記録するだけに留める |
| 取消も追記で表現する | UPDATE / DELETE の口を作らないことで、履歴の欠落を構造的に防ぐ |
| **取消の対象は ENTRY に限る** | 取消の取消を認めると、有効打刻の判定が再帰的になり読めなくなる。やり直したいなら新しい ENTRY を積む |
| **追記された ENTRY にも理由を必須にする** | 打刻漏れの補完は取り消す対象が無い。理由が無いと、なぜその時刻なのかが後から分からない |

### 3.1 打刻漏れの救済

出勤打刻を忘れた日は、取り消すべき行が存在しない。
**ENTRY の追記だけで訂正できる**ことを明示する。

| 状況 | 訂正の形 |
| --- | --- |
| 退勤を打ち忘れた | 退勤の ENTRY を追記する |
| 出勤を打ち忘れた | 出勤の ENTRY を追記する。既存の打刻は取り消さない |
| 時刻を間違えた | 対象の ENTRY を REVOCATION で取り消し、正しい ENTRY を追記する |

いずれも `approval` の訂正申請を経て承認されたものだけが追記される（BR-09）。
追記される打刻の `source` は `CORRECTION` になる。

### 3.2 ポート

```java
public interface TimeClockEventRepository {
    void append(EmployeeId employeeId, LocalDate workDate,
                TimeClockEvent event, ClockSource source, String reason);
    /** 取消。パーティションを絞るため workDate を必ず受け取る。 */
    void revoke(EmployeeId employeeId, LocalDate workDate,
                TimeClockEventId targetId, EmployeeId revokedBy, String reason);
    List<TimeClockEvent> findEffective(EmployeeId employeeId, LocalDate workDate);
    List<TimeClockEntry> findHistory(EmployeeId employeeId, LocalDate workDate);  // 取消も含む全履歴
    /** 退勤していない勤務日。締めていない全期間から探す（4 章）。 */
    List<LocalDate> findOpenWorkDates(EmployeeId employeeId, DateRange searchRange);
}

public interface DailyAttendanceRepository {
    Optional<DailyAttendance> find(EmployeeId employeeId, LocalDate workDate);
    List<DailyAttendance> findByPeriod(EmployeeId employeeId, DateRange period);
    /** 誰の勤怠かと、どの版で計算したかはポートの引数で運ぶ。 */
    void save(EmployeeId employeeId, DailyAttendance attendance, WorkRuleId workRuleId,
              long version);
}
```

`DailyAttendance` 自身は `employeeId` も `workRuleId` も持たない。
**計算結果そのものと、それが誰のどの規則によるものかは別の関心事**であり、
計算器（`DailyAttendanceCalculator`）はどちらも知らずに動く。
`daily_attendances` の `employee_id` / `work_rule_id` はポートの引数から埋める。

**更新・削除のメソッドを `TimeClockEventRepository` に置かない。**
`revoke` は取消行の `append` である。

`revoke` が `workDate` を受け取るのは、`time_clock_events` が `work_date` で
パーティション分割されているため。`id` だけで引くと全パーティションを走査する
（[DB設計書 4.1](DB設計書.md)）。

締め済みの判定は `shared` のポートを使う。

```java
// shared/domain。実装は approval/infrastructure
if (!monthClosureQuery.acceptsChanges(employeeId, YearMonth.from(workDate))) { ... }
```

**判定に使う月は打刻時刻の月ではなく `workDate` の月である。**
3/31 22:00 出勤 → 4/1 06:00 退勤の退勤打刻は 3 月として判定する。
打刻時刻で判定すると、締め済みの 3 月分を 4 月扱いで書き込めてしまう。

## 4. 勤務日の決定（BR-03）

日をまたぐ勤務は **出勤日に通算する。**
翌 03:00 の退勤打刻を前日の勤務として扱うため、打刻を受け付けるときに勤務日を解決する。

```java
private LocalDate resolveWorkDate(PunchCommand command) {
    LocalDate punchedOn = command.occurredAt().toLocalDate();
    if (command.type() == CLOCK_IN) {
        return punchedOn;                       // 出勤打刻はその日が勤務日
    }
    // それ以外は「まだ退勤していない勤務日」のうち最も新しいものへ紐づける
    return timeClockEvents.findOpenWorkDates(command.employeeId(), unclosedRange())
            .stream().max(Comparator.naturalOrder())
            .orElse(punchedOn);
}
```

| 状況 | 勤務日 |
| --- | --- |
| 4/7 13:00 出勤 → 4/8 03:00 退勤 | どちらも 4/7 |
| 4/7 に退勤済みで 4/8 09:00 出勤 | 4/8 |
| 4/7 の退勤打刻を忘れたまま 4/8 09:00 に出勤打刻 | **4/8。打刻は受け付ける。** 応答に「4/7 が未退勤」を警告として含める |

### 4.1 未退勤の探索範囲は「締めていない全期間」

第 1 版は前日 1 日だけを見ていた。これでは 2 つの問題が起きる。

| 問題 | 内容 |
| --- | --- |
| 検出漏れ | 金曜に退勤を打ち忘れて **月曜**に出勤すると、未退勤日が見つからない。金曜は永久に未完了のまま残り、提出の直前に発覚する |
| 運用のデッドロック | 翌日が営業日なら出勤打刻を拒否していた。訂正申請の承認が下りるまで **当日の打刻が一切できない**。BR-09 は承認を要求するので、その間の労働の証拠が残らない |

**打刻を拒否しない。** 一次証拠の記録を、別の日の不整合で止めてはいけない。

```java
// 応答に含める警告。エラーではない
{ "unclosedWorkDates": ["2026-04-07"] }
```

画面は「4/7 の退勤打刻がありません」と示し、訂正申請（SC-04）へ誘導する
（[画面設計書 4.1](../90_画面/画面設計書.md)）。

### 4.2 打刻の記録と日次計算を分ける

**打刻の追記は、日次計算が失敗しても成功させる。**

| 失敗の理由 | 打刻 | 日次計算 |
| --- | --- | --- |
| 就業規則が未設定 | **成功する** | 行わない。`calculationStatus = WORK_RULE_NOT_FOUND` を返す |
| 退勤していない | 成功する | 行わない。`calculationStatus = NOT_CLOSED` |
| 締め済みの月 | **拒否する（409）** | ― |
| 打刻順序の違反 | **拒否する（422）** | ― |

就業規則の未設定は計算側の都合であり、労働の事実とは関係がない。
これを理由に退勤打刻を拒否すると、**働いた証拠が残らない。**
締め済みと順序違反だけは、記録そのものが不正なので拒否する。

## 5. 休憩時間の検証（BR-08）

```java
public record BreakTimeRequirement(Duration workingTime, Duration actualBreak) {
    /** 労基法 34 条が要求する休憩時間。 */
    public Duration required() {
        if (workingTime.compareTo(Duration.ofHours(8)) > 0) return Duration.ofMinutes(60);
        if (workingTime.compareTo(Duration.ofHours(6)) > 0) return Duration.ofMinutes(45);
        return Duration.ZERO;
    }
    public boolean isSatisfied() { return actualBreak.compareTo(required()) >= 0; }
}
```

**不足していても計算は打刻どおりに行う。** 警告を出すだけに留める。
勝手に休憩を差し引くと、実際には働いていた時間が消えて賃金の不払いになるため。

この判定は `workingTime` と `breakTime` から一意に決まるので、
DB でも CHECK 制約として同じ式を置く（[DB設計書 3.2](DB設計書.md)）。
