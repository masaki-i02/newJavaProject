# 設計規約チェックリスト

| 項目 | 内容 |
| --- | --- |
| 文書番号 | KNT-DES-002 |
| 版 | 1.1 |
| 目的 | **設計書を書き終えたら、コミット前にこの一覧を上から確認する** |

---

## なぜこの文書があるか

コンテキストごとに設計書を書いていったところ、
**同じ種類の指摘が繰り返し現れた。** 第 2 回レビューでは、
第 1 回で挙がった 43 件のうち **11 件が別のコンテキストで再発** していた。
その後 03 / 04 / 05 のレビューでも、同じ種類の指摘がさらに繰り返された
（合計 127 件の指摘のうち、再発が 30 件以上）。

| 再発した指摘 | 回数 |
| --- | --- |
| `btree_gist` の宣言が無く DDL が適用できない | 2 |
| 閉区間と半開区間の混在 | 2 |
| 図と本文の乖離 | 2 |
| `updated_at` を更新するトリガが無い | 2 |
| 更新される表に楽観ロックが無い | 2 |
| API に `version` が無い | 2 |
| EXCLUDE の GiST と重複する B-tree インデックス | 2 |
| 検証環境と実施日の記載が無い | 2 |
| 未定義の型を使っている | 2 |
| DB で守れない範囲を明示していない | 2 |
| 依存図に無いコンテキスト依存を生む | 2 |
| 月中入社の社員が初月を締められない | 2 |
| 実行者が不在で状態が進まなくなる | 2 |
| 要件に無い概念を増やしている | 3 |
| 他コンテキストが所有する概念を API の応答に混ぜている | 3 |
| どのクエリにも使われないインデックス | 3 |

**個別に直しても、次のコンテキストでまた同じことが起きる。**
規約として明文化し、書き終えるたびに機械的に確認する。

---

## 1. 共通

- [ ] 要件定義書に無い概念を追加していないか。追加するなら要件を先に改訂したか
- [ ] 使っている型がすべて定義済みか（値オブジェクトの表に載っているか）
- [ ] 図（`.mmd`）と本文が一致しているか。図を直したら `npm run render` を実行したか
- [ ] 他コンテキストの設計書と、共通仕様の参照関係が正しいか

## 2. 期間・時刻

- [ ] **すべての期間が半開区間 `[from, toExclusive)` か。** 閉区間を混ぜていないか
- [ ] API が閉区間で受ける場合、`plusDays(1)` で変換することを明記したか
- [ ] 「最終日」を意味する値（退職日など）を、半開区間の上限にそのまま渡していないか
- [ ] 業務上の日時は `Clock`、`created_at` / `updated_at` は DB の `now()` で統一されているか

## 3. コンテキストの依存

- [ ] 他コンテキストの型を参照していないか。参照するなら [コンテキスト間依存図](アーキテクチャ設計書.md) に辺があるか
- [ ] 逆向きの問い合わせが必要な場合、**ポートを `shared` に置いて** 依存の追加を避けたか
- [ ] API のレスポンスに、他コンテキストが所有する概念を混ぜていないか

## 4. DB 設計書

### 4.1 適用できる DDL であること

- [ ] `EXCLUDE USING gist` を使うなら **`CREATE EXTENSION IF NOT EXISTS btree_gist;` を冒頭に書いたか**
- [ ] `CHECK` 制約に副問い合わせを書いていないか（PostgreSQL は許さない）
- [ ] 設計書から抽出した DDL **だけ** で適用できることを実際に確認したか

### 4.2 監査列

- [ ] `updated_at` を持つ表すべてに `set_updated_at()` トリガを適用したか
- [ ] **UPDATE される表に `version`（楽観ロック）を持たせたか**

### 4.3 制約

- [ ] 状態と付随カラムの整合を CHECK で守っているか（「承認済みなのに承認者が空」を作れないか）
- [ ] 算出式が他の列から決まるなら、その式を CHECK にしたか
- [ ] 他テーブルを参照する不変条件を制約トリガで守るか、**守らないなら「DB では防げないもの」に列挙したか**
- [ ] 一意制約は在籍者・現存分に限るべきか検討したか（部分一意インデックス）

### 4.4 インデックス

- [ ] **`EXCLUDE` が生成する GiST と重複する B-tree を置いていないか**
- [ ] 設計書の「主要なクエリ」すべてに、対応するインデックスがあるか
- [ ] 逆に、どのクエリにも使われないインデックスを置いていないか

### 4.5 検証

- [ ] **検証環境（PostgreSQL のバージョン・拡張）と実施日を併記したか**
- [ ] 制約が不正データを拒否することを、実際に実行して確認したか
- [ ] 正常系も確認したか（拒否ばかり確認して、通るべきものが通らない設計になっていないか）
- [ ] **検証では入力を 1 つだけ変えたか**（2 つ変えると何を証明したか分からなくなる）

## 5. API 設計書

- [ ] 更新系のリクエストに `version` を含めたか。`optimistic-lock-failure` をエラー一覧に載せたか
- [ ] エラーの `type` が粗すぎないか（`conflict` に複数の原因をまとめていないか）
- [ ] 一覧を返すとき、配列を裸で返さずオブジェクトで包んだか
- [ ] `date` の既定値を `application` 層が `Clock` から解決すると明記したか
- [ ] 一覧系の内部結合が、対象を意図せず絞っていないか（未来日入社・退職者が消えないか）
- [ ] 副作用のある操作（退職・異動など）で、閉じるべき期間をすべて列挙したか

## 6. 業務ルール

- [ ] **月中入社・月中退職の社員で成立するか**（初月・最終月が締められなくならないか）
- [ ] 月末月初、うるう年、日をまたぐ勤務で成立するか
- [ ] 締め済みの月に対する操作を拒否しているか
- [ ] 誤りが起きたとき、**社員に不利な方向へ倒れていないか**（賃金の過少払い・不当な控除）
- [ ] 要件の記述と設計の記述で、基準日や区間の表現が揃っているか
- [ ] **実行者が不在になる経路を洗い出したか**（退職・休職・部署廃止で、提出・承認・締めが誰にもできなくならないか）
- [ ] **副作用として自動で起きる状態遷移を、明示的な遷移と同じく型にしたか**（証跡に残せない遷移を作っていないか）
- [ ] **一次証拠の記録を、別の日の不整合や計算側の都合で止めていないか**
- [ ] **労働時間の帰属先（勤務日）と、割増の判定単位（暦日・週・月）を取り違えていないか**
- [ ] **制度による分岐と、暦日区分による分岐を混ぜていないか**
- [ ] 法定値には**下限だけでなく上限**も置いたか（割増の対象そのものを消せないか）
- [ ] **排他を主張する制約は、両方が成り立つ正当なケースが無いか先に探したか**

## 7. テスト観点

- [ ] テスト ID が要件 ID（`BR-xx`）から辿れる形か
- [ ] 境界値（区間の端、月初月末、0 件、上限ちょうど）を挙げたか
- [ ] 「型として存在しないので書けないテスト」がある場合、その旨を明記したか
- [ ] **正常系を、条件ごとに 1 行ずつ分けたか**（`FIXED` / `FLEX` を 1 行にまとめない）
- [ ] **「拒否された」ではなく「狙った制約で拒否された」ことを確認したか**（別の制約に先に引っかかっていないか）
- [ ] **閾値をまたぐ数字を選んだか**（「法定休日 2 時間 + 翌日 6 時間 = 8 時間」では、累積に数えても数えなくても結果が同じになる）
- [ ] **不変条件は、それを強制している場所に破れた値を渡して確かめたか**（compact constructor が守る条件を、その型のインスタンスに対して確かめても恒真）
- [ ] **既定値以外の設定でも計算が正しいか確かめたか**（規則の値をベタ書きの定数に置き換えても通るなら、規則を読んでいない）
- [ ] **ID は生成器が拾える形か**（`collect-tests.py` は接尾辞つき ID を黙って落とす）

## 8. 実装を変えたとき

- [ ] **その変更の根拠になった設計書の節を、同じコミットで直したか**
- [ ] 実装が設計書と違う判断をしたなら、**どちらが正しいかを決めて片方を直したか**（両方を残さない）
- [ ] 検査をやめたなら、**やめた理由を設計書に書いたか**（成立しない条件だった、上位の不変条件から導ける、など）
- [ ] 新しいテストに ID を振ったなら、**設計書の観点表に追記して一覧を再生成したか**

---

## 使い方

設計書を書き終えたら、この一覧を上から確認し、
**確認した結果を設計書の「制約の検証」節に残す。**
確認していない項目があるなら、未決事項として記録する。

**実装を変えたときは 8 章だけでも確認する。**
実装を直して設計書を戻さない抜けは、レビュー第 3 回で 3 件見つかった。
そのうち 1 件は「修正済みの欠陥を設計書がなお正しいと主張する」状態になっていた。

レビューで新しい種類の指摘が出たら、**この一覧に項目を追加する。**
同じ指摘が 2 回出たということは、規約になっていないということである。
