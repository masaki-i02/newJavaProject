# ADR 0002: ドメインモデルと JPA エンティティを分離する

- **ステータス**: 採用
- **日付**: 2026-09-01
- **関連**: [アーキテクチャ設計書](../02_詳細設計/アーキテクチャ設計書.md) 5 章

## 背景

業務ルールを表すオブジェクトと、テーブルに対応するオブジェクトを
同一のクラスにするかどうかを決める必要があった。

本プロジェクトの主題は「業務ルールを型で表現し、ありえない状態を作れなくすること」である。
一方で JPA には次の制約がある。

- エンティティは引数なしコンストラクタを必要とする
- 遅延ロードのためにフィールドを `final` にできない
- 上記により `record` にできず、不変オブジェクトにできない

## 検討した選択肢

| 案 | 内容 | 利点 | 欠点 |
| --- | --- | --- | --- |
| A | 分離する。ドメインは `record`、永続化は `@Entity`、両者を変換する | ドメインが不変にでき、DB なしで単体テストできる | テーブルごとに 30〜50 行の変換コードが増える。定義が 2 か所になる |
| B | 分離しない。`@Entity` をドメインとしても使う | 変換コードが不要で実装量が少ない | ドメインが可変になる。`record` も `sealed` も使えない |
| C | 一部だけ分離する。計算ロジックを持つものは分け、単純なマスタは兼用する | 労力と効果のバランスが取れる | 「どちらの方式か」を都度判断する必要があり、規約が曖昧になる |

## 決定

案 A（すべて分離する）を採用する。

## 根拠

**案 B は本プロジェクトの主題と両立しない。**
割増区分を `sealed interface` で表現し、打刻の状態遷移の網羅性をコンパイラに保証させる、
という設計の中心が、可変クラス前提では成立しない。実装量が減っても主張が消える。

**単体テストの速度と範囲が決定的に違う。**
分離していれば、深夜をまたぐ勤務や日跨ぎ勤務といった境界条件を、
データベースを一切起動せずに数秒で網羅できる。労働時間の計算は境界値の塊であり、
ここを軽量にテストできるかどうかがプロジェクト全体の進行速度を左右する。

案 C を採らなかったのは、**規約が曖昧になるとレビューで判断がぶれるため**である。
「これは計算ロジックを持つか」の線引きは主観的で、時間とともに侵食される。
一律に分離するほうが、規約として維持しやすい。

## 結果

- テーブルごとに変換コードが増える。これは受け入れる
- 同じ概念を 2 か所で定義するため、片方だけ直す事故が起こりうる。
  統合テストで「ドメイン → 永続化 → ドメイン」の往復が一致することを検証して防ぐ
- JPA エンティティはパッケージプライベートとし、ArchUnit の AR-05 で
  `infrastructure` の外から参照されないことを保証する
