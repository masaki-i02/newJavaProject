# ADR 0009: 1 インスタンスで運用し、スケールアウトしない

- **ステータス**: 採用
- **日付**: 2026-09-07
- **関連**: 要件定義書 2.2 / 7、ADR 0008

## 背景

M3-c（コンテナ化とデプロイ）を進めるにあたり、
**セッションの保存先を決める必要があった。**

現状は Spring Security の既定（`HttpSessionSecurityContextRepository` +
Tomcat の標準セッション）であり、**インメモリ**である。
つまり次の 2 つが起こる。

- インスタンスを 2 つにすると、要求が振り分けられた先によってログイン状態が違う
- 再デプロイのたびに全員がログアウトする

これは「見落とし」なのか「判断」なのかを決めないと、
読んだ人がどちらとも取れる状態が残る。

## 検討した選択肢

| 案 | 内容 | 利点 | 欠点 |
| --- | --- | --- | --- |
| A | Redis + spring-session を入れる | 複数インスタンスで動く。再デプロイでログアウトしない | 依存が 1 つ増える。運用対象が 1 つ増える。**増やす理由が無い** |
| B | **1 インスタンスで運用すると決める** | 依存が増えない。構成が単純 | 再デプロイでログアウトする。スケールアウトできない |
| C | 決めずに放置する | — | 見落としと区別がつかない |

## 決定

**B を採る。1 インスタンスで運用し、スケールアウトしない。**

## 根拠

### 1. 規模が要求していない

要件 2.2 の対象企業は**従業員 100 名・単一事業所**、
要件 7 の同時利用は **50 名**である。
1 インスタンスの Spring Boot が捌けない量ではない。

### 2. SLA を定義していない

要件 7 は「個人開発のため SLA は定義しない」と明記している。
可用性のためにインスタンスを増やす前提そのものが無い。

### 3. 再デプロイのログアウトは、この業務では許容できる

勤怠の利用は始業・終業に集中し、**深夜は無人**である。
夜間に入れ替えれば、ログアウトの影響を受ける利用者がいない。
ブルーグリーンやカナリアも同じ理由で持ち込まない。

### 4. 増やさないと決めることが、増やせるようにすることより安い

Redis を足すと、**運用の対象が 1 つ増える**（バックアップ・監視・版の更新）。
個人開発のポートフォリオで、使わない可用性のために
運用対象を増やすのは割に合わない。

## 結果

- **良くなったこと**: セッションの保存先が「見落とし」ではなく「判断」になった。
  デプロイ手順書が「夜間に止めて入れ替える」と書ける根拠ができた
- **諦めたこと**:
  - 無停止デプロイ。再デプロイのたびに全員が再ログインする
  - 水平スケール。負荷が増えたら垂直に上げる（コンテナのメモリ上限を上げる）
  - app の冗長化。落ちたら止まる
- **見直す条件**: 次のいずれか。
  - 同時利用が 200 名を超えた（1 インスタンスで捌けなくなる）
  - 事業所が増えて、深夜も誰かが打刻するようになった（止められなくなる）
  - 可用性が要件になった（SLA を定義することになった）

  そのときに入れるのは `spring-session-data-redis` である。
  `SecurityConfig` の `SecurityContextRepository` を差し替える形になるので、
  **アプリケーション層と `domain` には影響しない。**

## この判断に依存している設定

| 場所 | 内容 |
| --- | --- |
| `application-prod.yaml` | `hikari.maximum-pool-size: 20`（PostgreSQL の `max_connections` 100 に対して 1 インスタンスぶん）|
| `docker-compose.prod.yml` | `app` のレプリカを増やす設定を書かない |
| [デプロイ手順書](../08_運用/デプロイ手順書.md) | 「夜間に止めて入れ替える」 |
| Flyway | マイグレーションをアプリの起動時に流す。**同時に 2 つが流そうとすることが無い**ので、別ジョブに切り出していない |
