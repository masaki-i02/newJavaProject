# ADR 0001: パッケージを業務コンテキスト優先で分割する

- **ステータス**: 採用
- **日付**: 2026-09-01
- **関連**: [アーキテクチャ設計書](../02_詳細設計/00_共通/アーキテクチャ設計書.md) 3 章

## 背景

パッケージの最上位を何で分けるかを決める必要があった。
本システムには勤怠の集計、社員と組織、就業規則、申請と承認という、
性質の異なる 4 つの業務が含まれる。

## 検討した選択肢

| 案 | 内容 | 利点 | 欠点 |
| --- | --- | --- | --- |
| A | レイヤ優先<br>`domain` / `application` / `infrastructure` / `presentation` を最上位に置く | 日本の業務システムで最も一般的で、レイヤの概念を知っていれば読める | 1 つの機能を足すのに 4 か所を触る。関連するコードが離れる |
| B | 業務コンテキスト優先<br>`attendance` / `employee` / `workrule` / `approval` を最上位に置き、その中を層で分ける | 業務の区切りがパッケージに現れる。機能追加が 1 か所で済む | 層が最上位にないため、レイヤ構成を知らない人には見通しが悪い |

## 決定

案 B（業務コンテキスト優先）を採用する。

## 根拠

**パッケージ構成そのものを設計意図の説明にしたかった。**
`attendance` を開けば勤怠の全体像が見え、`approval` を開けば承認フローが完結している状態は、
それ自体がドメインの説明になる。レイヤ優先では「勤怠とは何か」がリポジトリ全体に散る。

もう一つの理由は、**検査できる規約が増えること**である。
案 A で書けるのは層の依存方向だけだが、案 B ではコンテキスト間の依存も検査できる。

```java
// 案 B でのみ書けるルール
"approval は attendance の domain と application だけを参照してよい。
 attendance の infrastructure を参照してはならない"
```

他コンテキストの `infrastructure` に触れるようになると、テーブルの都合が業務の境界を
越えて伝播し、分割した意味が失われる。この事故を機械的に防げるのは大きい。

案 A を採らなかったのは、慣習として一般的であること以外に積極的な理由が無かったためである。
「よく見る形だから」は、この規模の個人開発では選定理由として弱いと判断した。

## 結果

- コンテキスト間の依存を有向非巡回グラフとして定義し、ArchUnit の AR-06 / AR-07 で検査する
- 層が最上位に現れないため、アーキテクチャ設計書に完成形のツリーを明記して補う
- コンテキストが増えて ArchUnit のルールが管理しづらくなった場合は、
  Spring Modulith の導入を再検討する
