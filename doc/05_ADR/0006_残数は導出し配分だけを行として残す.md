# ADR 0006: 残数は付与と消化から導き、「どれから引いたか」の配分だけを行として残す

- **ステータス**: 採用
- **日付**: 2026-09-04
- **関連**: 要件定義書 BR-15 / BR-16 / [年次有給休暇 ドメインモデル設計書 3](../02_詳細設計/06_年次有給休暇/ドメインモデル設計書.md) / [ADR 0003](0003_履歴を持つマスタを系列と版に分ける.md)

## 背景

年次有給休暇には次の 4 つの出来事がある。

| 出来事 | 残日数への影響 |
| --- | --- |
| 付与（BR-14） | 増える |
| 取得の承認（BR-16） | 減る |
| 取得の取下げ（BR-16） | 戻る |
| 時効による失効（BR-15） | 減る |

しかも **消化は先入先出**であり（BR-15）、
どの付与から引いたかによって「いつ失効するか」が変わる。
「残 3 日」という数だけでは、それが来月失効するのかどうかを答えられない。

さらに、出勤率の再判定（[06 ドメインモデル設計書 2.5](../02_詳細設計/06_年次有給休暇/ドメインモデル設計書.md)）で
**過去に付与が増えることがある。**

## 検討した選択肢

| 案 | 内容 | 利点 | 欠点 |
| --- | --- | --- | --- |
| A | `employees.remaining_leave_days` のような**残数の列**を持ち、4 つの出来事で更新する | 参照が 1 行で済む | 更新箇所が 4 つ。1 つ落とすと静かにずれ、DB では検出できない。失効はバッチが要る |
| B | 残数も配分も**すべて導出**する（付与と承認済みの取得から毎回計算する） | 列が無いのでずれようがない | 再判定で付与が増えた瞬間、**過去の取得日の配分先が入れ替わる。** 失効の時期も変わり、以前の残数を説明できない |
| C | **残数は導出、配分（どの付与から引いたか）は行として残す** | 導出値の二重管理が無く、過去の配分は動かない | 参照のたびに集計する。取消で配分を外す処理が要る |

## 決定

**C を採る。**

- `paid_leave_grants`（付与）と `paid_leave_requests.grant_id`（配分）だけを持つ
- 残日数の列は持たない
- 失効の行も作らない（「付与日 + 2 年」だけで決まる純粋な関数である）

## 根拠

**A を採らない**のは、[CLAUDE.md 落とし穴 39](../../CLAUDE.md) がまさにこの形だからである。
導出できる値を列に持つなら、食い違いを DB で禁じなければならない。
ところが残数の整合は他のテーブルの集計に依存し、
**`CHECK` に副問い合わせは書けない**（落とし穴 8）。
守れない不変条件を列として置くと、「守られているように見える」だけが増える。

**B を採らない**のは、**決定と導出値を取り違えているから**である。
先入先出でどの付与を選ぶかは、**承認という行為の時点で下された決定**であって、
いつでも計算し直してよい値ではない。
毎回導出すると、再判定で古い付与が増えたときに
「去年の 10 月に取った 1 日が、実は別の付与から引かれていたことになる」という
**過去の書き換え**が黙って起きる。失効の時期が変わるので残数の履歴も説明できなくなる。

**失効を行にしない**のは、実行者が不在になる経路を作らないためである（落とし穴 26）。
バッチで失効行を作る設計は、バッチが動かなかった日に残数が過大になり、
しかもその状態が **DB 上は正しく見える。**
付与日から決まる関数なら、いつ計算しても同じ答えになる。

## 結果

- 残数の食い違いという種類の不具合が**構造として存在しない**
- 「なぜ今この残数なのか」を、付与と配分の行だけで説明できる
- 取消では**配分を外す**（`grant_id` を `NULL` に戻す）ことが必須になった。
  外し忘れると残数が戻らないので、`paid_leave_requests_state_check` で
  「取下げなのに配分が残っている」を作れなくしている
- 参照のたびに集計する。100 名規模では問題にならないが、
  対象が桁違いに増え、集計が実測で問題になったときは
  **導出結果のキャッシュ**（正は行のまま）を検討する。
  そのときも「残数を正とする列」には戻さない
