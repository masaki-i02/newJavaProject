# ADR 0003: 履歴を持つマスタを「系列」と「版」に分け、参照する側は系列を指す

- **ステータス**: 採用
- **日付**: 2026-09-01
- **関連**: 要件定義書 3 章（前提条件：就業規則）/ [就業規則 DB設計書 2.1](../02_詳細設計/02_就業規則・カレンダー/DB設計書.md) / [レビュー記録 第 2 回](../06_レビュー記録/02_詳細設計_第2回.md)

## 背景

就業規則は改定される。4 月に改定しても、3 月分の勤怠は当時の規則で再計算できなければならない
（要件定義書 3 章）。そこで規則に有効期間を持たせ、勤務日を指定して取得する形にした。

一方、社員がどの規則に従うかは個人ごとに決まる（固定時間制／フレックス）。
これも有効期間を持つ。**「規則の有効期間」と「社員への適用期間」の 2 つがある。**

第 1 版は次の形だった。

```
work_rule_assignments.work_rule_id ──> work_rules.id
```

レビューで **「改定した瞬間に全社員の就業規則が未設定になる」** ことが判明した。

改定は「現行の行の `valid_to` を閉じ、新しい行を作る」操作である。
適用行は古い行の `id` を指したままなので、
「適用期間には入っているが、その規則はもう有効ではない」として 0 件になる。
**勤怠計算が全社員で停止する。**

## 検討した選択肢

| 案 | 内容 | 利点 | 欠点 |
| --- | --- | --- | --- |
| A | 改定のたびに全社員の適用行を作り直す | スキーマを変えずに済む | 100 名ぶんの UPDATE が改定のたびに走る。**失敗すると一部の社員だけ旧規則を指す**。適用の履歴が改定の履歴で汚れる |
| B | 規則の行を更新し、旧内容を履歴テーブルへ退避する | 参照が切れない | 過去分の再計算で履歴テーブルを引く必要があり、参照経路が 2 本になる。「今」と「過去」でコードが変わる |
| C | **系列（不変の識別子）と版（有効期間つき）に分け、適用は系列を指す** | 改定は版を 1 行足すだけ。適用行に触れない | テーブルが 1 つ増える。解決が 2 段階になる |

## 決定

**案 C を採る。**

```sql
work_rule_series      -- 系列。改定をまたいで不変。社員はこれに紐づく
    ↑ series_id
work_rules            -- 版。改定のたびに 1 行増える。有効期間を持つ

work_rule_assignments.work_rule_series_id ──> work_rule_series.id
```

型も分ける。

```java
record WorkRuleSeriesId(UUID value) {}   // 系列
record WorkRuleId(UUID value) {}         // 版
```

## 根拠

**社員が結びつくのは「標準勤務という規則」であって「2024 年 4 月版の標準勤務」ではない。**
第 1 版はこの区別をせず、業務上 2 つある概念を 1 つのテーブルで表していた。

案 A は書き込み量の問題ではなく、**改定という 1 つの操作が全社員のデータを触る**ことが問題である。
就業規則の改定は会社の判断であり、社員個人の適用状態とは関係がない。
関係のないデータを触らずに済む形にする。

案 B は「今の規則」と「過去の規則」で引く先が変わる。
本システムは締め後の再計算や訂正の反映で **過去分を頻繁に引く**ので、
経路が 2 本あると必ず片方を書き忘れる。

案 C の代償は「解決が 2 段階になる」ことだが、これは 1 本のクエリで書ける。

```sql
FROM work_rule_assignments a
JOIN work_rule_series s ON s.id = a.work_rule_series_id
JOIN work_rules r       ON r.series_id = s.id
WHERE ... AND a.valid_from <= :date AND (a.valid_to IS NULL OR a.valid_to > :date)
          AND r.valid_from <= :date AND (r.valid_to IS NULL OR r.valid_to > :date)
```

2 つの排他制約（適用の重複禁止・版の重複禁止）により、結果は高々 1 件になる。

### 型を分ける理由

`WorkRuleId` と `WorkRuleSeriesId` はどちらも UUID である。
**同じ型のままだと、取り違えてもコンパイルが通る。**
この設計欠陥の一因は「UUID を UUID として扱っていた」ことにある。

## 結果

- 改定は **版を 1 行足すだけ**の操作になった。適用行は一切書き換えない
- 「版に隙間がある」（その日に有効な版が無い）という新しい異常が起こりうる。
  DB では防げないので、**未適用者の一覧**（`GET /api/work-rule-assignments/unassigned`）で検知する
- 系列そのものの廃止（`abolished_on`）を扱えるようになった
- `IT-WR-19`「改定後も 4.1 が規則を返す」を検証項目に加えた。
  **第 1 版でこの検証を書いていれば、設計段階で気づけた**

### 見直す条件

この形は「有効期間を持ち、他から参照されるマスタ」すべてに当てはまる。
本システムでは就業規則だけだが、**同じ形のマスタを追加するときは最初からこの形にする。**
CLAUDE.md の 2.3 に「履歴を持つマスタ」として記載した。
