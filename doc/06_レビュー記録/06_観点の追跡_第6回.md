# レビュー第 6 回: 設計書にあってテストが無い観点

| 項目 | 内容 |
| --- | --- |
| 対象 | 詳細設計書のテスト観点（`UT-xx-nn` / `IT-xx-nn`）と、テストコードの突き合わせ |
| 実施日 | 2026-09-09 |
| 進め方 | 観点を 3 群（BR-09/AUD・BR-10・BR-11）に分け、**3 エージェントに独立して調べさせた**。実装は禁じ、報告だけを出させた |
| 指摘数 | 21 件（うち 13 件が追跡の付け直し、8 件が検査の欠落）。派生して 7 件 |

---

## 1. きっかけ

`collect-tests.py` は突き合わせを**片方向しか**行っていなかった。

- 落としていた: 設計書に無い ID をコードが名乗っている
- **落としていなかった: 設計書にある ID をどのテストも名乗っていない**

後者は<strong>テスト数では絶対に検出できない</strong>。
テストは存在するテストしか検査しないからである
（`check-endpoints.py` を作るきっかけになった落とし穴 155 と同じ形が、
経路ではなく**観点**について起きていた）。

数えたところ、設計書の 984 個の ID のうち **21 個**を名乗るテストが 1 つも無かった。

---

## 2. 分類の結果

| 分類 | 件数 | 対応 |
| --- | --- | --- |
| **(A) 追跡が切れているだけ** | 13 | 同じ観点を確かめているテストが別の ID で存在した。`@DisplayName` に両方の ID を書き、生成器が複数 ID を拾えるようにした |
| **(B) 検査が無い** | 8 | テストを新設した |

(A) は「設計書が層ごとに同じ規則を書いている」ために起きる。
たとえば `UT-BR10-02`（ドメインモデル設計書）と `IT-APV-45`（API設計書）は同じ観点であり、
複数のリポジトリを束ねないと成立しないので<strong>結合テストにしか置けない</strong>。
ID を振り直さない（CLAUDE.md の決定事項）以上、**1 本のテストが 2 つの ID を名乗る**のが正しい。

---

## 3. うしろから出たもの

### 3.1 ID がずれていた（最も重い）

`ApproverPolicyTest` が名乗る `UT-BR11-04`〜`10` は、
**01 の設計書の採番と 1 つずつずれていた。**

| 番号 | 設計書（01） | テストコード |
| --- | --- | --- |
| `UT-BR11-04` | 部署長が承認時点で退職済み | 最上位の長の勤怠は人事が承認する |
| `UT-BR11-05` | 部署が廃止済み | 対象月のあとに退職した長はスキップ |
| `UT-BR11-06` | 根まで長がいない | 月中入社の基準日 |
| `UT-BR11-07` | 本部長本人の承認者 | 対象月に所属が無ければ `NONE` |

**両方向の突き合わせを足しても出てこない。** どちらの向きも「その ID は在る」で通るからである。
結果として、設計書には書いてあるのに**1 件も検査されていない観点が 5 つ**あった。

- 部署が廃止済み（`SkipReason.DEPARTMENT_ABOLISHED` はテストコード全体で 1 度も現れていなかった）
- 根まで長がいない
- 異動を挟む月の承認者
- 部署長が交代している月の承認者
- 退職日当日の所属と承認者

テストの ID を設計書の採番へそろえ、5 件を新設した。
`Approver.isApprovedBy` の 3 件（設計書のどこにも無かった）は
`UT-BR11-16`〜`18` として 05 の設計書に登録した。

### 3.2 設計書が自分と矛盾していた

05 のドメインモデル設計書 3.2 は
「**`ADMIN` へはエスカレーションしない。版 1.3 までそう書いていたが、
そのような経路は実装されていない**」と直してあった。
ところが **7 章の観点表（`UT-BR11-13`）だけが「`ADMIN` へエスカレーションする」のまま**だった。

表だけを読んで実装した人は、**設計書が禁じたセキュリティ上の迂回路**
（`ADMIN` に無条件の承認権を与え、BR-11 の 1〜4 をすべて飛ばす）を作ることになる。
表を本文に合わせ、あわせて「本文を直したら観点表も同じコミットで直す」ことを
落とし穴 192 として記録した。

### 3.3 本番コードに日本語の引数名が残っていた

`MonthAlreadyClosedException(YearMonth month, String 操作)` など 8 か所。

- **javac も ecj も何も言わない**（Java の仕様としては合法）
- **ArchUnit にも見えない**（バイトコードには引数名が無い）

源泉を読む検査（`check-identifiers.py`）を新設し、CI に入れ、
わざと違反を入れて落ちることを確かめた。

## 6. 自分の指摘が誤っていた 1 件

`UT-BR11-05`（廃止済みの部署）を最初に書いたとき、
「長を残したまま廃止する。空にすると `NO_MANAGER` でも通ってしまう」と書いた。
**逆だった。**

長が残っていると、判定の順序を入れ替えても同じ理由が返る（等価変異）。
順序に意味があるのは<strong>長がいない場合だけ</strong>で、
そちらが実際に起きる形（部署を廃止すれば部署長の在任も閉じる）でもある。

変異を当てて**生き残ったことで気づいた**。
書いたテストの正しさを、書いた本人の説明で判定しないこと（落とし穴 43・149）。

## 7. 道具の側で踏んだもの

変異を戻したあと、全数実行で `UT-BR11-04` と `UT-BR11-14` が落ちた。
**源泉は正しく（`git diff` は clean）、`git status` も clean。**

原因はビルド出力だった。変異を戻す道具がファイルを書き戻したとき、
その mtime が<strong>変異後にコンパイルした `.class` より古い</strong>ままになり、
Gradle の増分コンパイルが再コンパイルを飛ばして
**変異したクラスがビルドに残り続けていた**（落とし穴 193）。

製品の欠陥とまったく見分けがつかない形で落ちるので、
戻したあとに `touch` することを道具に入れた。
