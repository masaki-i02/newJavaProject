### 1.2 「正しく見える」制約が正しいデータを拒んでいた

最も学びが大きかったのは 04 の
`monthly_settlements_exclusive_check`（時間外と不足は同時に発生しない）である。

「どちらも同じ対象労働時間から導かれるので、両方が正になるのは計算の誤り」
という説明を書き、DB の CHECK にし、ドメインの不変条件にもした。
**論理は一貫していたが、前提が間違っていた。**

前提は「所定総労働時間 < 法定労働時間の総枠」だった。
2026 年 6 月（暦日 30 日・所定労働日 22 日）ではこれが逆転し、
所定 10,560 分に対して総枠は 10,285 分になる。
**適法な月の清算結果を、DB もドメインも保存できなかった。**

レビュアーが実際に INSERT して再現した。

```
ERROR:  new row for relation "monthly_settlements" violates check constraint
        "monthly_settlements_exclusive_check"
```

自分の検証（IT-SET-12「正常な `FIXED` / `FLEX` の清算結果」）は
**1 行に 2 つの制度をまとめており、しかも所定 < 総枠 の月しか試していなかった。**
入力を 1 つずつ変えていれば設計段階で気づけた。

## 3. 横断的な決定

| # | 決定 | 理由 |
| --- | --- | --- |
| 1 | **DB は PostgreSQL 16 とする** | 設計書には 17 と書きながら、検証はすべて 16 で行っていた。検証できない版を設計書に書かない |
| 2 | **`PremiumType` と `MonthClosureQuery` は `shared.domain` に置く** | 2 つ以上のコンテキストが使う概念を片側に置くと依存が循環する。`shared` なら新しい辺が増えない |
| 3 | **`WorkingTimeSystemType` は永続化と表示のためだけの判別値** | 分岐は `sealed interface` に対する網羅性検査つき `switch` で行う。enum で分岐すると考慮漏れが実行時まで分からない |
| 4 | **履歴を持つマスタは系列と版に分け、参照する側は系列を指す** | 版を指すと改定した瞬間に全参照が切れる |
| 5 | **API は他コンテキストが所有する概念を返さない** | 社員番号・氏名・部署は `employee` から引く。持っていない情報の提供者にならない |
| 6 | **期間はすべて半開区間。API のパラメータ名も `toExclusive`** | 名前で「その日を含むのか」を示す |

要件定義書も 2 か所改訂した（版 0.3）。

| 箇所 | 内容 |
| --- | --- |
| BR-01 | 秒を分へそろえる向き（常に労働時間が長くなる側） |
| BR-05 | 対象労働時間の定義、清算期間と在籍期間の交差、所定総が法定総枠を上回る月の扱い |

**設計で必要になった概念は、要件を先に改訂してから設計書に書く。**
「要件に無いものを増やしている」は 3 回繰り返した指摘である。

## 5. 教訓

| # | 教訓 |
| --- | --- |
| 1 | **同じ指摘が 2 回出たら、それは規約になっていない。** 個別に直さず、チェックリストに項目を足して機械的に確認する |
| 2 | **排他を主張する制約は、両方が成り立つ正当なケースが無いか先に探す。** 論理が一貫していても前提が誤っていることがある |
| 3 | **正常系の検証を 1 行にまとめない。** 条件ごとに分けて、入力を 1 つずつ変える。まとめた 1 行が欠陥を隠した |
| 4 | **「拒否された」ではなく「狙った制約で拒否された」ことを確認する。** 別の制約に先に引っかかると、狙った検証は行われていない |
| 5 | **一次証拠の記録を、別の日の不整合や計算側の都合で止めない。** 打刻を拒否すると働いた事実が残らない |
| 6 | **労働時間の帰属先（勤務日）と、割増の判定単位（暦日・週・月）は別物。** 取り違えると賃金が過少になる |
| 7 | **実行者が不在になる経路を洗い出す。** 退職・部署廃止で、提出・承認・締めが誰にもできなくなる状態は 2 回作った |
| 8 | **副作用として自動で起きる状態遷移も、明示的な遷移と同じく型にする。** そうしないと証跡に残せない |
| 9 | **採用するバージョンと検証に使うバージョンをそろえる。** 検証できない版を設計書に書かない |
