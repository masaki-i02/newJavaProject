## 1. 設計を変えるに至った重大な指摘

### 1.1 部署長本人の勤怠が永久に締められない【最重要】

**指摘**
自己承認を避けて親部署へ遡る設計だが、部署長の兼任を許しているため、
**本部長は所属部署の長も親部署の長も自分自身**になる。
根まで遡っても承認者が得られず、BR-10 の「提出済 → 承認済」に到達できない。
結果として **月次の締め（UC-12）が完了しない。**

この配置は、DB設計書 v0.1 の検証データ（田中一郎が営業本部と第一営業部の両方の長）で
実際に再現していた。**自分で作った検証データが欠陥を示していたのに気づいていなかった。**

**対応**
BR-11 に「根まで遡っても承認者が得られない場合は人事担当（`HR`）が承認する」を追加。
要件定義書 v0.2 で改訂し、`resolvedFrom` に `HR_FALLBACK` を追加した。

### 1.2 承認者の在籍判定の基準日が誤っていた

**指摘**
BR-11 の基準日は対象月の初日だが、承認行為は翌月に行われる。
「対象月初日には在籍していたが、承認時点では退職している部署長」が承認者として返り、
**その承認を誰も実行できない。**

**対応**
基準日を 2 つに分けた。所属部署の決定は基準日（対象月初日）、
**承認者の在籍判定のみ承認実行時点**とする。要件定義書 BR-11 に明記。

### 1.3 月中入社の社員は初月を締められない

**指摘**
BR-11 を機械的に適用すると、4/15 入社の社員は 4 月初日に所属が無く、承認者が導出できない。

**対応**
BR-11 の基準日を「対象月の初日、ただし当月に所属開始がある場合は所属開始日」に改めた。

### 1.4 在籍期間と所属期間で区間の流儀が違い、退職日当日が消える

**指摘**
在籍判定は閉区間（退職日を含む）、所属期間は半開区間（`valid_to` を含まない）で、
同一ドメイン内に 2 つの流儀が混在していた。
退職時に `assignments.valid_to = retiredOn` とすると、
**退職日当日は在籍しているのに所属が無い**状態になり、最終日の承認者が導出できない。

**対応**
すべての期間を半開区間（`DateRange`）に統一。
`Employee.activePeriod()` が `retiredOn.plusDays(1)` へ変換する形にし、
退職 API の副作用として「翌日で閉じる」ことを明記した。

### 1.5 BR-11 の実装場所が 2 か所で二重定義されていた

**指摘**
アーキテクチャ設計書は `approval/domain.ApproverResolver`、
ドメインモデル設計書は `employee/domain.OrganizationChart.managerOf` が
BR-11 を実装すると宣言していた。**両方作れば業務ルールが分裂する。**

**対応**
責務を分割した。

| コンテキスト | クラス | 担うもの |
| --- | --- | --- |
| `employee` | `OrganizationChart` | 事実の導出（所属、祖先、部署長） |
| `approval` | `ApproverPolicy` | 承認の業務ルール（自己承認の禁止、退職者スキップ、HR フォールバック） |

### 1.6 `btree_gist` が設計書に無く、DDL がそのままでは適用できない

**指摘**
`EXCLUDE USING gist (employee_id WITH =, daterange(...) WITH &&)` は
`btree_gist` 拡張が必須。設計書のどこにも記載が無く、
**本設計の看板である 2 つの EXCLUDE 制約が記載どおりでは 1 つも作れない。**

**対応**
DB設計書 3.0 に `CREATE EXTENSION IF NOT EXISTS btree_gist;` を追加。
設計書から抽出した DDL のみで適用できることを再検証した。

### 1.7 要件に無い「雇用形態」を増やし、要件にある計算式を壊していた

**指摘**
`employmentType`（`FULL_TIME` / `PART_TIME` / `CONTRACT`）は要件定義書に一度も現れない。
`PART_TIME` を許すと、所定 8 時間を前提とする BR-04 / BR-05 が実態と合わなくなり、
**短時間勤務者に不当な欠勤控除が発生する。**

**対応**
`employmentType` を削除。要件定義書 3.1 に
「全社員の所定労働時間は 1 日 8 時間。短時間勤務は対象外」を明記した。

### 1.8 `GET /api/me` が依存図に無いコンテキスト依存を生んでいた

**指摘**
`GET /api/me`（`employee`）が `workingTimeSystem`（`workrule` の概念）を返していた。
コンテキスト間依存図に `employee → workrule` の辺は無く、AR-06 に抵触する。

**対応**
`GET /api/me` から労働時間制度を削除。フロントエンドが `workrule` の
エンドポイントから別途取得する形にした。
アーキテクチャ設計書 3.2 に「API の都合でコンテキストの境界を崩さない」を明記。

### 1.9 検証結果が主張を証明していなかった

**指摘**
「同一のクエリが対象日によって異なる部署長を返す」ことの検証で、
**`date` だけでなく `departmentId` も変えて実行していた。**
これでは部署長の交代と社員の異動が混在し、証明になっていない。

**対応**
`departmentId` を固定し `date` のみを変えて再実行。結果を DB設計書 7 章に差し替えた。
検証環境（PostgreSQL 16 / `btree_gist` 有効 / 実施日）も併記した。

## 3. 対応しないと判断したもの

| # | 指摘 | 判断 |
| --- | --- | --- |
| 1-8 | 部署階層を 3 階層に強制する | **強制しない。** 組織改編で 4 階層になる可能性があり、DB で縛ると改編のたびにマイグレーションが必要になる。要件の「3 階層」は現状の記述であって制約ではないと解釈する |
| 2-9 | 遡及異動を許可する | **今回は拒否のまま。** 締め済み月の承認者が変わる問題があり、締め処理の設計と併せて決める必要がある。要件 10 章 #6 として管理 |
| 1-9 | アカウントロックを実装する | **M1-c まで持ち込まない。** 閾値も解除手段も未定のまま列だけ作ると、ロックされた社員を復旧できなくなる |

## 4. この回で得られた教訓

| # | 教訓 |
| --- | --- |
| 1 | **自分で作った検証データを疑う。** 1.1 の欠陥は、自分の検証データに現れていたのに見逃していた |
| 2 | **検証は入力を 1 つだけ変える。** 2 つ変えると何を証明したのか分からなくなる（1.9） |
| 3 | **区間の流儀は 1 つに統一する。** 閉区間と半開区間の混在は、境界の 1 日が消えるという形で必ず現れる（1.4） |
| 4 | **要件に無いものを増やさない。** 増やした列が、要件にある計算式の前提を壊すことがある（1.7） |
| 5 | **DB で守れない範囲を明示する。** 黙って抜けているのが最も危険（2-6） |
