## 1. この文書と一覧の関係

**テストケースの内容は詳細設計書が正である。** 本書はその上に載る規約を定める。

```
詳細設計書（正）── collect-tests.py ──> テストケース一覧（生成物）
    ↑                                        ↑
  設計を直すのはここ                    見るだけ。手で書かない
```

図を `.mmd` から `.png` へ変換するのと同じ考え方である。
**一覧を手で書くと、設計書を直したときに必ず片方だけが古くなる。**

```bash
cd doc/_tools && python3 collect-tests.py
```

生成器は **ID の重複を検出して警告する。** 実際、この仕組みを入れた直後に
`UT-BR11-01`〜`03` が 01 と 05 の両方で使われていることが見つかった
（05 側を `UT-BR11-13`〜`15` へ改めた）。

## 2. ID の規約

| 接頭辞 | 対象 |
| --- | --- |
| `UT-EMP-xx` | 社員・在籍期間 |
| `UT-BR11-xx` | 承認者の導出（BR-11） |
| `UT-WR-xx` | 就業規則・労働時間制度 |
| `UT-CAL-xx` | 会社カレンダー |
| `UT-ATT-xx` | 打刻・日次集計 |
| `UT-BR04-xx` | 週 40 時間超 |
| `UT-BR05-xx` | フレックスの清算 |
| `UT-BR12-xx` | 36 協定 |
| `UT-BR09-xx` | 打刻の訂正 |
| `UT-BR10-xx` | 提出・承認・締め |
| `UT-AUD-xx` | 監査証跡 |

**業務ルールに直接対応するものは `UT-BRxx-nn` とし、要件 ID をそのまま含める。**
型や値オブジェクトの検証は対象を表す接頭辞（`EMP` / `WR` / `ATT` など）にする。

`UT-BR11` のように **1 つのルールが複数のコンテキストにまたがる場合、ID は通番を共有する。**
コンテキストごとに 01 から振り直すと衝突する。

### 2.1 ID をコードに対応させる

```java
@Test
@DisplayName("UT-BR05-14 所定総 > 総枠 の月で対象労働が両者の間にあると、時間外と不足が両方とも正になる")
void overtimeAndShortageCanBothBePositive() { ... }
```

**`@DisplayName` の先頭に ID を置く。**
「この業務ルールのテストはどこか」を検索一発で辿れる状態にするための規約であり、
レビューでも実装でも最初に使う。

**一覧の ID がすべてコードに現れること**を機械的に検査したいが、その仕組みは未整備である
（7 章 未決事項 #1）。当面は手で確認する。

> **逆向きも見る。** 「一覧にあるのにコードに無い」（未実装）だけでなく、
> **「コードにあるのに一覧に無い」**（採番したまま設計書に戻していない）も追跡可能性の穴である。
> レビュー第 3 回では後者が 7 件見つかり、一覧の件数が現状を表していなかった。

## 4. テストの書き方

### 4.1 時刻は必ず固定する

```java
private static final Clock FIXED =
        Clock.fixed(Instant.parse("2026-05-01T00:00:00Z"), BusinessZone.ID);
```

**`LocalDateTime.now()` を直接呼ばない**（CLAUDE.md 4.3）。
`Clock` を DI しているのは、承認時点の在籍判定（BR-11）のように
**「いつ実行したか」で結果が変わる**ロジックがあるためである。

### 4.2 入力は 1 つだけ変える

同じ前提から入力を 1 つだけ変えた組を作る。

```java
// UT-BR05-04 / 05 / 06 は「対象労働時間」だけが違う
settlement(targetWorking = 9_000)   // 総枠未満・所定未満 → 不足
settlement(targetWorking = 10_400)  // 総枠未満・所定超   → どちらも 0
settlement(targetWorking = 11_100)  // 総枠超             → 時間外
```

**2 つ変えると、何を証明したのか分からなくなる**（CLAUDE.md 落とし穴 12）。

### 4.3 正常系を 1 つにまとめない

制度・期間・状態の組み合わせは、条件ごとにケースを分ける。

> 月次清算の第 1 版は正常系を「正常な `FIXED` / `FLEX`」の 1 ケースにまとめ、
> しかも所定 < 総枠 の月しか試していなかった。
> **この 1 行が、適法な月を保存できない欠陥を隠した**（CLAUDE.md 落とし穴 24）。

### 4.4 例外は型とメッセージの両方を見る

```java
assertThatThrownBy(() -> new PremiumRates(
        new BigDecimal("0.10"), new BigDecimal("0.25"), new BigDecimal("0.35")))
        .isInstanceOf(IllegalArgumentException.class)
        .hasMessageContaining("法定外残業の割増率が法定下限を下回っています");
```

**「例外が出た」だけを見ない。** 別の検証に先に引っかかると、
狙った不変条件は確かめられていない（CLAUDE.md 落とし穴 25）。

### 4.5 不変条件は「強制している場所」を叩く

compact constructor が強制している不変条件を、**その型のインスタンスに対して**
確かめてはいけない。破れていれば生成の時点で例外になるので、
アサーションまで到達しない。**恒真である。**

```java
// 意味がない。DailyAttendance が存在する時点で必ず成立している
assertThat(attendance.baseTime().plus(...)).isEqualTo(attendance.workingTime());

// 意味がある。強制している当の場所に、破れた値を渡す
assertThatThrownBy(() -> new DailyAttendance(..., Duration.ofHours(8), ..., Duration.ofHours(7), ...))
        .hasMessageContaining("内訳の合計が実労働時間と一致しません");
```

第 1 版は前者を全ケースの末尾に置いていた。**18 か所の恒真な行だった。**

同じことが ArchUnit のルールにも言える。
ルールが緑なのは「規約が守られている」からとは限らず、
対象が 1 件も無い、条件が誤っていて何にも当たらない、でも緑になる。
**わざと違反したクラスを置いて、落ちることを確かめる**（CLAUDE.md 落とし穴 31）。
`ArchRuleSelfTest` が AR-01〜09 のすべてについてこれを行う。

同様に、**テストの代役（テストダブル）に業務ロジックを持たせない。**
所定労働日数の数え方を代役側に置くと、そのテストは本番のコードを 1 行も検査しない。
数え方は `CompanyCalendar` の既定実装に置き、代役は「その日が何の日か」だけを答える。

### 4.6 テストデータの組み立て

固定時間制・フレックスの就業規則、社員、打刻列はビルダーを用意する。

```java
WorkRule rule = aFixedRule().scheduled("09:00", "18:00").breakMinutes(60).build();
TimeClockSequence seq = punches().in("13:00").breakFrom("18:00").breakTo("19:00")
                                 .out("2026-04-08T03:00").build();
```

**ビルダーの既定値は「正常な値」にする。**
ケースごとに変えたい 1 項目だけを上書きすれば、4.2 が自然に守られる。

## 5. 単体テストで検証しないもの

| 内容 | どこで守るか |
| --- | --- |
| DB の制約が不正データを拒否すること | 結合テスト（[IT 一覧](../04_結合テスト/テストケース一覧.md)、104 件） |
| コンテキスト間・レイヤ間の依存方向 | ArchUnit（AR-01〜09） |
| 締め済みからの状態遷移 | **型として存在しない**（下記 5.1） |
| 打刻テーブルへの UPDATE / DELETE | ポートに口が無い + DB 権限 |
| API の形式・ステータスコード | 結合テスト |

### 5.1 型で保証していて、テストが書けないもの

```java
// AttendanceTransition は Closed からの遷移を permit していない。
// 書こうとするとコンパイルが通らないので、実行時のテストとして存在しえない
```

| ID | 内容 |
| --- | --- |
| `UT-BR10-08` | 締め済みからの遷移が存在しないこと |

**「テストが無い」のではなく「テストが不要になった」**ことを記録する。
一覧から抜くと、後の読み手には検証漏れに見える。

### 5.2 まだ書けないもの（実装待ち）

| ID | 内容 | 何を待っているか |
| --- | --- | --- |
| `UT-ATT-15` | 前日が未退勤のまま出勤打刻 | 打刻リポジトリ（`application` 層） |
| `UT-ATT-16` | 金曜が未退勤で月曜に出勤打刻 | 同上 |

**未実装であることを明示する。** 一覧に ID があってテストが無いと、
「書き忘れ」なのか「まだ書けない」のかが後から分からない。

同じ理由で、次の 4 つも実行時のテストを持たない。

| 保証 | 仕組み |
| --- | --- |
| フレックスの規則から `scheduledStart` を読めない | `sealed interface` + `record` |
| 労働時間制度を追加したときの考慮漏れ | 網羅性検査つき `switch`（`default` 句を書かない） |
| `WorkRuleId` と `WorkRuleSeriesId` の取り違え | 別の型にしてある |
| 不正な値オブジェクトの生成 | compact constructor（**生成そのものが例外**なので、テストは「例外になること」を見る） |
| 法が認めない深夜帯 | `enum`（**そもそも書けない**ので、テストは「値が 2 つのままであること」を見る） |

下 2 つだけは実行時に確かめられるので、`UT-WR-04` `UT-WR-09`〜`12` などがある。
上 3 つはコンパイラが保証するので、テストを書いても常に通る。**書かない。**
