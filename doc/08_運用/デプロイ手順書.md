## 1. 初回構築

```bash
git clone <このリポジトリ>
cd newJavaProject

cp .env.example .env
chmod 600 .env          # ★ 他のユーザから読めないようにする
vi .env                 # KINTAI_DB_PASSWORD を必ず変える

docker compose -f docker-compose.prod.yml up -d --build
```

`app` と `db` の両方が `healthy` になれば起動している。

```bash
docker compose -f docker-compose.prod.yml ps
curl -fsS http://localhost:8080/actuator/health
```

### 起動しないとき

**`.env` の渡し忘れは起動の失敗として現れる。**
`application-prod.yaml` は DB 接続の既定値を持たないので、
未設定なら `'url' must start with "jdbc"` で落ちる。

> **これは設計である。** 既定値を持たせると、
> 環境変数を渡し忘れたコンテナが**黙って localhost の開発 DB を探しに行く**。
> 同居していれば繋がってしまい、本番のつもりで開発データを壊す。
> 起動しないほうがはるかに安全である（CLAUDE.md 落とし穴 123 と同型）。

## 2. 初期データ

**管理者を 1 人だけ手で作る。** そこから先は画面で登録できる。

```bash
docker compose -f docker-compose.prod.yml exec db \
  psql -U "$KINTAI_DB_USER" -d "$KINTAI_DB_NAME" -c "
    INSERT INTO employees (id, employee_number, name, email, hired_on, roles)
    VALUES (gen_random_uuid(), 'E0001', '管理者', 'admin@example.com',
            CURRENT_DATE, ARRAY['EMPLOYEE','HR','ADMIN']);"
```

パスワードは `ADMIN` が設定して口頭で伝える（BR-13）。
**メールでのリセットは設けていない**（退職者に再割り当てされたアドレスへ送る事故を避けるため）。

続けて、**その年度の会社カレンダーを登録する。**
登録しないと給与連携（BR-18）の分母が求まらず、出力が 422 で拒否される。

```
POST /api/calendars/bulk
{ "from": "2026-04-01", "toExclusive": "2027-04-01",
  "rules": [{"dayOfWeek":"SATURDAY","dayType":"NON_LEGAL_HOLIDAY"},
            {"dayOfWeek":"SUNDAY","dayType":"LEGAL_HOLIDAY"}],
  "overrides": [{"date":"2026-04-29","dayType":"NON_LEGAL_HOLIDAY","name":"昭和の日"}] }
```

## 3. 版の更新

```bash
git pull
docker compose -f docker-compose.prod.yml up -d --build app
```

**マイグレーションはアプリの起動時に流れる**（Flyway）。別のジョブにしていない。
1 インスタンス運用なので、同時に 2 つが流そうとすることが無い。

| 決定 | 理由 |
| --- | --- |
| **前方修正のみ。ロールバックしない** | Flyway Community に undo は無い。適用済みのマイグレーションは書き換えず、新しい版で `ALTER TABLE` する（CLAUDE.md「適用済みマイグレーションの変更」）|
| **`validate-on-migrate: true`** | 適用済みの SQL が書き換わっていたら起動を止める。黙って進むほうが危険である |
| **`clean-disabled: true`** | 本番で `flyway clean` を打てないようにする |
| **停止時間を許容する** | 夜間に入れ替える。勤怠は始業・終業に集中し、深夜は無人である。ブルーグリーンやカナリアは持ち込まない |

**更新の前にバックアップを取る。**
マイグレーションが失敗したときに戻す先が要る（[バックアップとリストア](バックアップとリストア.md)）。

### DB の権限

`V1__extensions_and_functions.sql` が `CREATE EXTENSION btree_gist` を実行する。
PostgreSQL 13 以降の trusted extension なので**データベースのオーナーなら通る**が、
最小権限のアプリ用ロールでは通らない。

**いまは 1 つのロールで動かしている。** 分けるなら、
マイグレーション用（オーナー）とアプリ用（DML のみ）を分け、
Flyway だけ前者で流すジョブに切り出すことになる。
1 インスタンス・個人開発の規模では分けていない。

## 4. 停止

```bash
docker compose -f docker-compose.prod.yml stop app   # アプリだけ止める
docker compose -f docker-compose.prod.yml down       # 両方止める（ボリュームは残る）
```

**`down -v` を打たない。** ボリュームごと消える。

`server.shutdown: graceful` を設定してあるので、
進行中の要求を終えてから止まる（猶予 30 秒）。
一括締めは 100 名ぶんを 1 トランザクションで進めるので、
即座に落とすとどこまで進んだかが分からなくなる。

## 5. HTTPS

**このリポジトリは HTTPS を終端しない。**
リバースプロキシ（nginx / Caddy / ALB など）の後ろに置く。

`application-prod.yaml` は `forward-headers-strategy: framework` を設定してあるので、
`X-Forwarded-Proto` を見てスキームを判定する。
これが無いと、`Secure` クッキーが HTTP と判定されて送られなくなる。
