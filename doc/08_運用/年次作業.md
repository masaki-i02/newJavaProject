**毎年 12 月に行う。** 忘れると翌年に止まる。

## 1. 打刻のパーティションを足す

`time_clock_events` は年でパーティションを切ってあり、
`V4` が **2026〜2030 と `DEFAULT`** を作っている。

`DEFAULT` があるので 2031 になっても即座には落ちない。
**問題はそのあとである。** `DEFAULT` に 2031 の行が入ったあとで
2031 のパーティションを `ATTACH` しようとすると失敗する
（既存の行が新しいパーティションの範囲に重なるため）。

```sql
-- 2030 年 12 月に、2031 年ぶんを足す
CREATE TABLE time_clock_events_2031 PARTITION OF time_clock_events
    FOR VALUES FROM ('2031-01-01') TO ('2032-01-01');
```

**新しいマイグレーションとして足す。** 手で打たない。
適用済みのマイグレーションは書き換えない。

`DEFAULT` に行が入ってしまった場合は、
`DETACH` → 行の移動 → `ATTACH` の順で直す。先に足すほうがはるかに安い。

## 2. 翌年度の会社カレンダーを登録する

**登録しないと、翌年度の給与連携（BR-18）が出せない。**

割増賃金の基礎額の分母（労基則 19 条 1 項 4 号）は年度全体の所定労働日数から決まる。
未登録の日は**所定労働日として扱われる**（登録漏れを休日と誤ると
通常勤務に休日割増が付いて過払いになるため）ので、
登録しないと年間 365 日として数えられ、**単価が法定を約 33% 下回る。**

そのため、未登録の日が 1 日でもある年度は `422 calendar-not-registered` で拒否する。

```
POST /api/calendars/bulk
{ "from": "2027-04-01", "toExclusive": "2028-04-01",
  "rules": [{"dayOfWeek":"SATURDAY","dayType":"NON_LEGAL_HOLIDAY"},
            {"dayOfWeek":"SUNDAY","dayType":"LEGAL_HOLIDAY"}],
  "overrides": [ ... 祝日 ... ] }
```

**祝日は曜日で決まらない。** 曜日の規則を当ててから個別に上書きする。

> **その年度の給与を 1 度でも出したあとは、分母を動かす変更ができなくなる。**
> 法定休日と所定休日の付け替えのように所定労働日数を変えない訂正は通るが、
> 所定労働日を休日に変える訂正は `409 fiscal-year-used-by-payroll` になる。
> **年度が始まる前に確定させておく。**

## 3. 36 協定の年度が変わる

`AgreementUsage` の年度は 4 月始まりで固定してある（BR-12）。
実際の 36 協定の起算日が 4 月 1 日でないなら、
**協定に合わせて定数を変える**必要がある。

> **割増賃金の基礎額の分母の年度と混同しない。**
> こちらは賃金規程が定める 1 年（3.6 の月末締めに対応）であり、
> 36 協定と同じ区切りになるのは結果であって理由ではない。
> 片方を動かしても、もう片方は動かない。

## 4. 年休の付与は自動である

年休の付与は毎日 2:30 のバッチが行う（`grantAsOf`）。
到来済みの未処理分をすべて作るので、**年次の手作業は要らない。**
止まっていないことだけを確かめる。

```sql
SELECT granted_on, count(*) FROM paid_leave_grants
 GROUP BY granted_on ORDER BY granted_on DESC LIMIT 5;
```
