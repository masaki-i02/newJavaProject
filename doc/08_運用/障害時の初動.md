# 障害時の初動

| 版 | 0.1 |

## まず見る 3 つ

```bash
# 1. どちらが落ちているか
docker compose -f docker-compose.prod.yml ps

# 2. アプリは要求を受けられるか
curl -fsS http://localhost:8080/actuator/health/readiness

# 3. 直近のログ
docker compose -f docker-compose.prod.yml logs --tail=200 app
```

| `readiness` | 意味 | 次にすること |
| --- | --- | --- |
| `UP` | 要求を受けられる | アプリの問題ではない。リバースプロキシと DNS を見る |
| `DOWN` | DB へ繋がらない | db の `ps` と `logs` を見る |
| 応答なし | プロセスが落ちている / 起動中 | `logs` を見る。起動直後なら 60 秒待つ |

**`liveness` と `readiness` を分けてある。**
分けないと、Flyway がマイグレーションを流している最中に
「まだ受けられない」ことを表せない。

## よくある止まり方

| 症状 | 原因 | 直し方 |
| --- | --- | --- |
| 起動直後に `'url' must start with "jdbc"` | `.env` を渡していない | `.env` を作る。**既定値へ黙って落ちない設計である**（[デプロイ手順書](デプロイ手順書.md) 1）|
| 起動時に Flyway の checksum エラー | 適用済みのマイグレーションが書き換わった | **書き換えを戻す。** 新しい版で `ALTER TABLE` する（CLAUDE.md「適用済みマイグレーションの変更」）|
| `too many clients` | 接続プールの合計が `max_connections` を超えた | `hikari.maximum-pool-size`（既定 20）と PostgreSQL の `max_connections`（既定 100）を突き合わせる。テストで一度踏んでいる（落とし穴 82）|
| OOMKill される | JVM がコンテナの上限を知らない | `JAVA_TOOL_OPTIONS=-XX:MaxRAMPercentage=75` が渡っているか（Dockerfile で設定済み）|
| ディスクが埋まる | ログのローテーションが効いていない | compose の `logging.options.max-size` / `max-file` を確認する |
| 打刻が 500 で失敗する | 実装の不備 | **応答に理由は載らない設計である**（内部の構造を外へ出さない）。ログのスタックトレースを見る |

## 監査証跡はログではなく DB にある

**5 年保持の対象はログではない。**
承認・年休・給与連携の証跡は表として残っている。

| 見たいこと | 表 |
| --- | --- |
| 誰がいつ提出・承認・締めたか | `approval_events` |
| 年休の申請と決裁 | `paid_leave_request_events` |
| 誰がいつどの月の給与データを出したか | `payroll_exports` / `payroll_export_targets` |
| 打刻と、その訂正 | `time_clock_events`（取消行を追記する形で残る） |

アプリケーションログは**一時的**なものとして扱う
（アーキテクチャ設計書 6.5）。障害調査のためにあり、監査のためではない。

## やらないと決めていること

| 対象 | 理由 |
| --- | --- |
| 監視 SaaS（Datadog / Sentry など） | `/actuator/health` と `docker logs` で足りる規模。賃金データを外部へ送る判断が別に要る |
| Prometheus + Grafana | メトリクスを常時見る人がいない |
| 分散トレーシング | サービスが 1 つしかない |
| HA / フェイルオーバ | 要件 7 が SLA を定義しないと明記している |
