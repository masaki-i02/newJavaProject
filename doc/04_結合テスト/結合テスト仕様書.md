## 2. 実行環境

**実物の PostgreSQL 16 に対して実行する。Testcontainers を使う。**

```java
@Testcontainers
abstract class IntegrationTestBase {
    @Container
    static final PostgreSQLContainer<?> DB =
            new PostgreSQLContainer<>("postgres:16-alpine");
}
```

| 決定 | 理由 |
| --- | --- |
| **H2 を使わない** | `EXCLUDE USING gist`・レンジパーティション・配列型・生成列が再現できない。通っても意味がない |
| バージョンを 16 に固定する | 設計書の DDL はすべて 16 で検証している。**検証できない版を使わない**（CLAUDE.md 落とし穴 21） |
| コンテナを全テストで共有する | 起動が最も重い。クラスごとに立てると現実的な時間で終わらない |
| **タイムゾーンを `Asia/Tokyo` に固定する** | `time_clock_events_validate_trigger` が `AT TIME ZONE` を使う。JVM とコンテナの両方で固定する |
| `hibernate.jdbc.time_zone` は **設定しない** | JDBC 層が `time` 型まで変換し、深夜帯 22:00–05:00 が別の時刻として読み込まれる（CLAUDE.md 落とし穴 1） |

### 2.1 スキーマの適用順

DDL には依存がある。**Flyway のマイグレーションもこの順に並べる。**

```
V1__extensions.sql          btree_gist（EXCLUDE の前提）
V2__employee.sql            employees / departments / assignments / managerships
V3__workrule.sql            work_rule_series / work_rules / work_rule_assignments / company_calendars
V4__attendance.sql          time_clock_events（パーティション）/ daily_attendances / slices
V5__settlement.sql          monthly_settlements / weekly_overtimes
V6__approval.sql            monthly_attendances / approval_events / correction_requests / items
```

`btree_gist` は 01 と 02 で必要。03 以降では不要だが、
**マイグレーションの先頭に置く**（CLAUDE.md 落とし穴 7）。

### 2.2 スキーマそのものの検証

制約を試す前に、**スキーマが期待どおりに出来上がっていること**を確かめる。
ここが崩れていると、以降の制約テストは「制約が無いから通った」のか
「守れているから通った」のかを区別できない。

`IT-SCH-01`〜`04`。どの業務コンテキストにも属さないので、
[アーキテクチャ設計書](../02_詳細設計/00_共通/アーキテクチャ設計書.md) の 9 章が正である。

### 2.3 データの後始末

**打刻テーブルは追記専用なので `DELETE` しない方針である。**
テストでは方針の例外として、各テストの後にトランザクションをロールバックする。

| 方式 | 使いどころ |
| --- | --- |
| `@Transactional` + ロールバック | 大半のケース |
| テーブルの `TRUNCATE ... CASCADE` | 制約トリガが `DEFERRABLE` で効かないケース、シナリオテスト |

## 3. 制約テスト（104 件）

[テストケース一覧](テストケース一覧.md) を参照。

| コンテキスト | 件数 | 重点 |
| --- | --- | --- |
| 社員・組織 | 14 | 期間の重複、部署階層の循環、平文パスワードの拒否 |
| 就業規則・カレンダー | 22 | **改定後も規則が引けること**、法定値の上限、適用開始日 |
| 勤怠（打刻・日次集計） | 22 | **他人の打刻を取り消せないこと**、日跨ぎ、暦日をまたぐ法定休日労働 |
| 勤怠（月次清算） | 20 | **所定総 > 総枠 の月が保存できること**、清算期間、36 協定の判定 |
| 申請・承認・締め | 26 | 遷移の飛び越し、代理提出、取下げ、自己承認の禁止 |

### 3.1 「拒否された」で終わらせない

```java
assertThatThrownBy(() -> insert(row))
        .rootCause()
        .hasMessageContaining("work_rules_statutory_daily_check");   // 制約名まで見る
```

**期待した制約で拒否されたかを確認する。**
別の制約に先に引っかかると、狙った検証は行われていない（CLAUDE.md 落とし穴 25）。

### 3.2 正常系を条件ごとに分ける

拒否のケースだけでは、**制約が正しいデータまで拒んでいないか**が分からない。

| ID | 正常系 |
| --- | --- |
| `IT-WR-11` | 別系列なら同じ期間の版を作れる |
| `IT-WR-14` | 月中入社の社員に、入社日から適用できる |
| `IT-ATT-18` | 所定休日の勤務日に法定休日労働を計上できる（日曜へまたいだ勤務） |
| `IT-SET-12` / `IT-SET-13` | 正常な `FIXED` / `FLEX`（**1 行にまとめない**） |
| `IT-SET-14` | **所定総 > 総枠 の月で時間外と不足が両方とも正** |
| `IT-APV-17` | 取り下げた申請と同じ勤務日に再申請できる |

> `IT-SET-14` は第 1 版の欠陥を捕まえる。
> 正常系を「正常な `FIXED` / `FLEX`」の 1 行にまとめたことで見逃していた。

## 4. API テスト

各 API 設計書のエラー表 1 行につき 1 ケースとする。
`@WebMvcTest` ではなく **`@SpringBootTest` + 実 DB** で行う。
モックのリポジトリでは、DB 制約に由来する `409` が再現できない。

| 観点 | 内容 |
| --- | --- |
| 形式 | 半開区間のパラメータ（`from` / `toExclusive`）、日時にオフセットを含めないこと |
| 判別可能ユニオン | `FIXED` の応答に `flextime` が出ないこと、`FLEX` の応答に `fixedTime` が出ないこと |
| エラー | RFC 9457 の `type` が設計書のとおりであること。**`status` ではなく `type` で区別できること** |
| 楽観ロック | `version` 不一致で `409 optimistic-lock-failure` |
| 権限 | ロール不足で `403`、閲覧範囲外で `403`。**未認証は `401`** |
| 他コンテキストの概念 | 応答に社員番号・氏名・部署が **含まれないこと**（設計規約チェックリスト 3） |

### 4.1 閲覧範囲は「見えないこと」を検証する

```java
// 一般社員が他人の勤怠を取得しようとする
mockMvc.perform(get("/api/employees/{other}/attendances", otherId).with(user(employee)))
       .andExpect(status().isForbidden());
```

**画面が隠していても API が返せば漏洩する。**
要件 4.1 の閲覧範囲の表について、行ごとに「見える」「見えない」の両方を検証する。

**ユースケースをまたいだ通しの業務。** 単体でも制約でも捕まらない欠陥を狙う。

| ID | シナリオ | 狙い | 要件 |
| --- | --- | --- | --- |
| `IT-SCN-01` | **1 か月の通し**：打刻 20 日 → 提出 → 承認 → 締め | M1 の骨格。これが通らないと何も始まらない | BR-02 / BR-10 |
| `IT-SCN-02` | **日をまたぐ勤務を含む月**：土曜 22:00 → 日曜 06:00 を含めて締める | 勤務日と暦日の区別が、集計から締めまで一貫しているか | BR-03 / BR-07 |
| `IT-SCN-03` | **打刻漏れ → 訂正申請 → 承認 → 再提出 → 締め** | 訂正の承認が日次と月次の両方を再計算し、月次勤怠が下書きへ戻るか | BR-09 / BR-10 |
| `IT-SCN-04` | **提出後に本人が打刻しようとする** | 提出済では打刻が拒否され、訂正申請は受け付けられるか | BR-10 |
| `IT-SCN-05` | **差戻し → 修正 → 再提出 → 承認** | 差戻しの理由が証跡に残り、下書きが打刻を再び受け付けるか | BR-10 |

| `IT-SCN-08` | **部署長本人の勤怠を締める** | BR-11 の遡りで人事へ到達し、承認できるか | BR-11 |

| `IT-SCN-11` | **締めたあとに打刻・訂正申請・カレンダー変更・規則の遡及適用を試みる** | 4 つの経路すべてが `MonthClosureQuery` で拒否されるか | BR-10 |

| `IT-SCN-16` | **20:00 → 翌 02:00 を保存して集計** | `timestamptz` を往復しても深夜 4 時間が保たれるか（落とし穴 1） | BR-06 |
| `IT-SCN-17` | **土曜 22:00 → 日曜 06:00 を保存して集計** | 法定休日の判定が暦日で行われ、深夜と重なった区間が保存できるか | BR-07 |
| `IT-SCN-18` | **2 人の社員に別々の規則を適用** | 互いの規則を引かないか（落とし穴 42） | BR-05 |

### 5.1 なぜシナリオが要るのか

第 1 回・第 2 回のレビューで見つかった重い欠陥は、**どれも単体テストでは捕まらなかった。**

| 欠陥 | 単体で捕まらなかった理由 | 捕まえるシナリオ |
| --- | --- | --- |
| 部署長本人の勤怠が永久に締められない | 承認者の導出は正しく動いていた。**締めまで通して初めて詰まる** | `IT-SCN-08` |
| 規則を改定すると全社員の規則が消える | 改定も参照も単体では正しい。**改定した後に引いて初めて 0 件になる** | `IT-SCN-09` |
| 退職者の最終月を誰も提出できない | 提出も承認も締めも個別には動く。**実行者がいないことは通しでしか分からない** | `IT-SCN-07` |
| 月中入社の初月が計算できない | 日次も月次も個別には動く。**初月を締めようとして初めて止まる** | `IT-SCN-06` |

**「個々の部品は正しいが、つないだら進めなくなる」**のがこのシステムの典型的な欠陥である。
シナリオテストはそれを狙う。

### 5.2 シナリオの書き方

```java
@Test
@DisplayName("IT-SCN-07 月中退職の最終月を人事が代理提出して締められる")
void closeFinalMonthOfRetiredEmployee() {
    var employee = 社員を登録する().入社("2020-04-01").退職("2026-09-20");
    9月の勤務日に打刻する(employee);
    日次を計算する(employee, 9月);

    // 本人はもうログインできない
    assertThatThrownBy(() -> 提出する(employee, 9月, as(employee)))
            .hasMessageContaining("在籍していません");

    人事が代理提出する(employee, 9月,理由: "退職者（最終在籍日 2026-09-20）の代理提出");
    承認する(employee, 9月, as(承認者));
    締める(employee, 9月, as(人事));

    assertThat(状態(employee, 9月)).isEqualTo(CLOSED);
    assertThat(証跡(employee, 9月)).extracting(ApprovalEvent::eventKind)
            .containsExactly(PROXY_SUBMIT, APPROVE, CLOSE);
}
```

| 規約 | 内容 |
| --- | --- |
| **証跡まで検証する** | 状態が `CLOSED` になっただけでは足りない。誰が何をしたかが記録されているか |
| **中間状態も検証する** | 最後だけ見ると、途中で意図しない経路を通っていても気づけない |
| ヘルパは日本語で書く | シナリオは業務の記述であり、読めることが第一 |
| 1 シナリオ 1 トランザクションにしない | 実際の業務は複数のリクエストにまたがる。まとめると締めの排他が検証できない |
